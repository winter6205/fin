# Plan: Question and task runtime completion

**Tracker:** [#406](https://github.com/winter6205/fin/issues/406). This issue contains the complete plan; task labels are internal to this plan.
**Goal:** Complete the approved Runtime contract for model-proposed task reconciliation, durable active-run input sequencing, grounded task completion, and safe restore/applicability.
**Approach:** Close the remaining host-wide and Runtime-owned paths through the existing send, task-state, and grounded-assessment seams. One model proposal reconciles each accepted input before dependent work; the Grounded Answer peer assesses only the resulting committed task and scope; Runtime remains the sole authority that validates and applies task state. Keep peer-owned assessment and source-authority production in their existing plans, and use issue #392 as the only integrated acceptance contract.
**Related gap issues:** [#397](https://github.com/winter6205/fin/issues/397), [#398](https://github.com/winter6205/fin/issues/398), and [#399](https://github.com/winter6205/fin/issues/399).
**Acceptance authority:** The approved [#392 version 1.0 resolution](https://github.com/winter6205/fin/issues/392#issuecomment-6061003025).
**Spec link:** [specs/question-task-runtime.md](../specs/question-task-runtime.md), [specs/question-grounded-answer.md](../specs/question-grounded-answer.md)
**External prerequisites:** The shared contract in T1 of [plans/question-task-runtime.md](question-task-runtime.md) must be accepted before implementation. The grounded assessment producer in [plans/question-grounded-answer.md](question-grounded-answer.md) and current source-scope / host-gate facts must be available before Runtime completion can be demonstrated. Materialized #392 fixtures and independent expected records are owned once by T1 of [plans/question-source-scope-completion.md](question-source-scope-completion.md), tracked by [#404](https://github.com/winter6205/fin/issues/404); this plan consumes those assets and does not create another acceptance specification.
**Per-bullet loop (all implementation bullets):** TDD → relevant typecheck+tests → verification-before-completion. After all bullets, run one code-review phase (GATE BLOCKED → review-report-repair), then final verification-before-completion. Do not weaken or replace a pinned behavior test until T1 records the explicit authorization and reason required by `.claude/rules/test.md`.
**Design intent:** Keep the existing host Module deep at a small Interface: callers observe durable acceptance, ordering, and a typed result while the Implementation hides admission and handoff details. Keep task-state authority in AgentState/checkpointer for Locality. An internal ordering mechanism may be chosen during implementation; it must not become a second task or persistence authority. Introduce another Seam only if a second real Adapter is needed; this plan does not preselect a new Module.

   - **Inherits:** “Do not delete tests or weaken assertions to make a build pass. A removed or replaced test must be covered by an equal or stronger test and include the reason, authorization, and explanation in the commit body.” (`.claude/rules/test.md`)
   - **Surface:** The existing host send contract and its pinned concurrency and task-switch tests referenced by [#397](https://github.com/winter6205/fin/issues/397) and [#398](https://github.com/winter6205/fin/issues/398).
   - **Acceptance:** Before implementation changes the 409 expectation or company-change heuristic tests, the operator's explicit authorization and reason are recorded for the migration; the replacement cases are at least as strong as the tests they replace. The send-contract review records whether empty, invalid/negative, overflow, concurrent, and exception inputs apply, gives a reason for each non-applicable class, and routes any applicable behavior not settled by the approved specs to an explicit decision before code. No pinned test is silently weakened.
   - **Completion:** A second owner can record the same authorization and applicability decisions without being prescribed a code shape or test path.
   - Status: [ ] blocked — requires explicit operator authorization and a recorded reason before changing tests that pin current behavior.

2. **T2 — Reconcile accepted inputs with one model-proposed task decision** — tag: `[implementation]`
   - **Inherits:** “Every accepted input receives one semantic reconciliation before dependent work. The model proposes the decision; the host validates and persists a consistent task transition, reconciliation marker, and execution disposition together. No separate classifier or second task store is introduced.” ([Runtime spec](../specs/question-task-runtime.md#confirmed-decisions-and-provenance))
   - **Surface:** The existing host-agent accepted-input model proposal and Runtime validation/commit path.
   - **Acceptance:** Each accepted message, valid question reply, and explicit restore request gets exactly one model-proposed reconciliation before dependent work. The proposal accounts for the new goal relative to the committed task: a same-company change of goal cannot silently continue under a stale task; a company mention alone cannot force a switch when the requested goal is still comparison or progress; and a multi-company request is evaluated as a whole. Runtime commits only a valid proposal, advances input history once, and changes task version only for a material change to goal, expected result, or necessary conditions. Progress may preserve applicable work. Taskless dialogue remains taskless; a clarification created during a transition binds to the resulting task. No extra classifier, second model call for switch detection, or independent agent loop is added. Invalid, missing, or failed proposals stop dependent work with a typed outcome and an explicit exit condition.
   - **Completion:** A second implementer may choose different prompt/state wiring while preserving one proposal before commit and Runtime as the only validator.
   - Status: [ ] pending
   - [blocks: T3, T4, T5, T6]

3. **T3 — Durably accept and sequence input during an active run** — tag: `[implementation]`
   - **Inherits:** “The host maintains one active graph execution per thread; a busy graph does not justify a second invocation, blanket rejection, or automatic cancellation.” An input during delayed work “must be durably accepted and sequenced through the existing per-thread execution.” ([Runtime spec](../specs/question-task-runtime.md#runtime-decision-contract); [#397](https://github.com/winter6205/fin/issues/397))
   - **Surface:** The host-wide existing send door, per-thread execution admission, and authoritative AgentState/checkpointer path.
   - **Acceptance:** While work is delayed, a send can be durably accepted and ordered for reconciliation through the active execution without starting a second graph run or returning the existing blanket-busy rejection. Busy checking and execution admission cannot race so that an accepted input is lost or two executions start. Every accepted input advances history once and is reconciled through T2 before dependent work. A failed checkpoint application preserves the last consistent state, and the response does not claim durable acceptance without evidence. Boundary tests cover every applicable class recorded in T1, including concurrent submission and exception paths; each failure has a typed outcome and each fallback has an explicit `// EXIT:` condition. An internal ordering mechanism may be used, but durable task authority remains the existing AgentState/checkpointer.
   - **Depends on:** T1 and T2.
   - **Completion:** A second implementer may choose another admission or ordering mechanism while preserving durable sequence, one active execution, and the existing task authority.
   - Status: [ ] pending
   - [blocks: T4, T5, T6]

4. **T4 — Keep cancellation reports and late receipts bound to originating work** — tag: `[implementation]`
   - **Inherits:** “Every in-flight operation and late receipt stays tied to its originating task and execution; adoption requires current permission, applicability, and evidence checks.” “The host records what cancellation was requested and what the run control actually reported; it never claims an external effect was undone without evidence.” ([Runtime spec](../specs/question-task-runtime.md#runtime-decision-contract); #392 J16/J19)
   - **Surface:** The existing host run-control and receipt path, Runtime task application, and authoritative checkpoint.
   - **Acceptance:** A reconciled cancellation affects only supported work; its result distinguishes requested intent from the actual run-control report and never asserts rollback of an external effect without evidence. A late receipt cannot overwrite or complete the current or replacement task. Runtime adopts it only after current task/source applicability, permission, and evidence checks pass. Failed state application keeps the last consistent checkpoint and prevents dependent work from proceeding on the unapplied transition. Failure classes remain distinct, each failure has a typed outcome, and each fallback has an explicit `// EXIT:` condition.
   - **Depends on:** T2 and T3.
   - **Completion:** A second implementer may choose a different internal receipt or cancellation representation while preserving origin binding, current-state validation, and truthful outcomes.
   - Status: [ ] pending
   - [blocks: T5, T6]

5. **T5 — Apply grounded assessments only to their committed basis and observed host gates** — tag: `[implementation]`
   - **Inherits:** “An assessment uses only the currently committed task/input and source-scope basis. Runtime first reconciles each accepted user input once. Grounded assessment begins only after the required task and scope state is committed.” Runtime “validates the proposal against the current basis and host checks, then alone applies and persists the outcome.” ([Grounded Answer spec](../specs/question-grounded-answer.md#inputs-and-result); [#399](https://github.com/winter6205/fin/issues/399))
   - **Surface:** The existing Grounded Answer result boundary, Runtime outcome application, and peer-owned current source-authority and host-gate facts.
   - **Acceptance:** The assessment contract carries enough committed task, task-version, scope, and receipt-origin basis for Runtime to reject an assessment for another task or obsolete scope before applying it. A changed input revision alone does not invalidate otherwise unchanged, applicable work. The grounded peer produces its assessment only after task and scope commitment; Runtime alone applies it. Completion is reachable for a supported whole goal with no material gap and observed passing permission, source identity/version, receipt, and persistence gates. Missing assessment or missing gate evidence never passes by default. Partial support, material gaps, taskless turns, and system failures remain distinct from task completion. Each failure has a typed outcome and each fallback has an explicit `// EXIT:` condition.
   - **Depends on:** T2–T4; the Grounded Answer assessment producer and Source Scope / host-gate producers must satisfy their existing peer plans.
   - **Completion:** A second implementer may choose another basis representation while preserving current-task validation, peer ownership of semantic assessment, and observed host gates.
   - Status: [ ] pending
   - [blocks: T6]

6. **T6 — Restore archived work through reconciliation and current applicability checks** — tag: `[implementation]`
   - **Inherits:** “A thread has one current task and may keep locatable archived tasks. Restore is explicit and rechecks current conditions, source authority, versions, and evidence applicability.” Saved scope is not current permission; old results remain historical until current checks support adoption. ([Runtime spec](../specs/question-task-runtime.md#confirmed-decisions-and-provenance))
   - **Surface:** The existing host-agent archive/checkpoint/history path and the same accepted-input reconciliation and assessment interfaces used by current work.
   - **Acceptance:** An explicit request for a listed archive is recorded once and reconciled through T2. The outgoing current task remains locatable, and the restored task becomes current only after checking current conditions, effective source scope and permission, source identity/version, and evidence applicability against current receipts. A prior answer, saved verification flag, summary, or input-revision mismatch alone cannot authorize or reject adoption. Stale clarification replies and failed checkpoint application cannot reactivate or overwrite a different task; failure preserves the last consistent state with a truthful typed outcome. Reload, compaction, and bounded original-input recovery retain the approved provenance and permission rules.
   - **Depends on:** T2–T5; current source-scope facts must be available from their owning plan.
   - **Completion:** A second implementer may choose another archive/checkpoint representation within the shared contract while preserving explicit restore and current applicability checks.
   - Status: [ ] pending

## 并行边界说明

**能同时跑的。** 阶段 1 的 A / B / C 三条线没有共享可变状态：A 只在 fin 内产出解析与切分能力，B 只在 **iknow-memory** 进程内产出检索能力，C 只产出语料资产与标注。三者的交汇面只有「跨仓对齐基线」章节与双方约定字段名——那是**只读**契约，不是共享写入面。

**什么会卡住什么。**

1. **基线改一行，全场停一次。** 基线章节是唯一共享面。任一侧要改它，必须先同步另一侧并重新过 sha256 相等门禁，再重启受影响的分阶段线。禁止单侧改基线后继续推进。
2. **阶段 0 卡住一切。** 阶段 1 三条线的入口都是"阶段 0 出口"——数字口径未定稿就动手，等于把建议值当契约，B 的接口与 C 的规模都会返工。
3. **阶段 2 卡在 A ∩ B。** fin 的推送需要 B 侧契约字段真实落地才能验；B 侧的"不二次切分"需要 A 侧推送真实块文本才能验。任一侧未达出口，阶段 2 不能开。
4. **阶段 3 卡在 C ∩ D。** 消融要在完整数据集上跑全量配置，并发要打真实推送链路；数据集没达标或推送幂等没过，评测数字没有意义。
5. **E1 与 E2 互不阻塞**，但两者都要在"同一份数据集 + 同一条推送链路"上跑，否则两侧数字不可合并。
6. **报告合并口径**：长文档召回与跨文档多跳召回是 **iknow-memory** 侧的评测维度，其数字由检索服务侧 spec 产出；fin 侧报告在合并时**只消费、不重算、不重复建模**，fin 侧评测维度清单中出现这两项的条数 = 0。

## 实现阶段说明（一次声明，两仓通用）

**每颗 tracer bullet 的循环：**

1. `test-driven-development` —— 先写失败测试，再写最小实现，再重构。
2. typecheck + tests —— Python 侧 `uv run pytest -q`（opt-in 标记另跑，如 `uv run pytest -q -m eval`）；默认套件不得读取大语料、不得启动检索服务进程、不得访问外网。
3. `verification-before-completion` —— 用真实运行结果说话，不以"应该能过"结案。
4. 一个 commit，落在 ticket 分支上（一颗 bullet = 一个 commit）。

**复杂度门槛**（行数、圈复杂度、参数个数、克隆率等）不写进 bullet 的 Acceptance，由 `complexity-anti-drift` 的 `references/thresholds.md` 统一裁决；bullet 只约束可观察行为与具名结构。

**收尾：** 全部 bullet 落地后，对整轮 diff 做**一次** code review（不 per-commit 重复），review 基准为 `specs/corpus-retrieval.md` 的 46 条 Success Criteria、跨仓对齐基线章节，以及仓库既有 Standards。跨仓改动还需复核：字段名逐字一致（`source_ref`、`degraded`、`degraded_reasons`、8 个能力键）、数字口径未在本地另立一套。

# Plan: permanent corpus upload and indexing

**Goal:** An operator can upload a supported source outside a research thread; fin durably stores the original, asynchronously parses and chunks it, pushes retrievable units, and tracks iknow-memory graph indexing as a separate job.
**Approach:** Restore a visible upload entry on the workspace home, then turn the synchronous ingest endpoint into a durable job whose raw-object, parse, chunk, and push stages can resume after restart. PDF parsing reuses the shared `fin.corpus.parsers` page/region core delivered by thread-attachment T2d; fin keeps ownership of deterministic chunking, while iknow-memory owns its separately queued graph-index job. A successful push is not reported as graph-index readiness.
**Spec links:** [`specs/corpus-serve-ingest.md`](../specs/corpus-serve-ingest.md), [`specs/corpus-ops-depth.md`](../specs/corpus-ops-depth.md), [`specs/thread-attachment-source-read.md`](../specs/thread-attachment-source-read.md), [`specs/graph-index-standard-fast.md`](../specs/graph-index-standard-fast.md).
**Sibling plans:** thread PDF parser seam: [`thread-attachment-source-read.md`](thread-attachment-source-read.md) T2d; bounded company `read_source`: [`../../iknow-memory/plans/bounded-source-read.md`](../../iknow-memory/plans/bounded-source-read.md) T1 (merged); iknow graph-index orchestration: [`../../iknow-memory/plans/corpus-index-job-orchestration.md`](../../iknow-memory/plans/corpus-index-job-orchestration.md). First wave: this plan's T1 and the iknow orchestration plan's T1 run in parallel to pin the cross-repo contract while attachment T2a completes its resource measurement.
**Per-ticket loop (implementation bullets):** tdd → targeted typecheck and tests. After all implementation bullets land, run one end-of-round code-review phase, repair BLOCKED findings, then verification-before-completion and the project commit rule.

## ACR

bounded-context-guardian: yes — fin owns permanent raw sources, parsing, deterministic chunking, and push; iknow-memory owns graph extraction/indexing; thread attachment state and indexes stay private to their thread.
input-contract-tests: yes — bullets cover missing/empty and invalid uploads, exact and over-cap sizes, duplicate/concurrent submissions, dependency faults, restart recovery, and replacement/invalidation boundaries.
error-handling-enforcer: yes — each failed stage has a typed status/EXIT, explicit recovery or terminal behavior, and no empty success; compensation failure remains visible.
complexity-anti-drift: yes — the sequence separates API/state decisions, durable submission, parser/chunk/push, and graph-index orchestration; it adds no graph node or second splitter.
minimal-change-verifier: yes — reuses the workspace home, corpus object-store/parser/chunk/push seams, and bounded source-read contract; does not add a second library, ranking implementation, or automatic thread-to-corpus conversion.

## Settled contract and open seams

- **Inherits:** ADR 0047 keeps thread attachment and permanent corpus ingest as separate doors; ADR 0037 and `specs/corpus-retrieval.md` keep parsing and deterministic chunking in fin; ADR 0043 keeps raw bytes in the object store and metadata/pointers in fin; ADR 0069 runs entity descriptions from the iknow extract/index job, not from push or query.
- **Inherits:** the company source locator remains `{document_id, version, unit}`; pushed chunks carry the canonical `source_ref`; exact company-unit reads use iknow-memory's bounded `read_source` contract. iknow distinguishes per-source text-search readiness from corpus-wide graph/C readiness. No model-supplied path or thread id widens access.
- **Inherits:** iknow-memory `plans/bounded-source-read.md` T1 is merged and remains complete; this plan consumes its bounded exact-`source_ref` read contract without reopening it.
- **Open for T1:** accepted-response/job identity, fin's durable submission states, retry/replacement semantics, whether to retain the existing 50 MiB upload cap or set a different finite cap, whether unsupported format is rejected before acceptance or fails as a job, how `document_id` is derived from filename/company/period and how `format`/`doc_type` are validated before a stable job identity exists, how the operator sees per-source text result alongside corpus-wide graph/C readiness, and the status polling contract. The current `corpus-serve-ingest` spec describes a synchronous endpoint and must be amended before implementation.
- **Current runtime gap:** the historical `plans/corpus-serve-ingest.md` T5 says the upload control landed, but current `App.tsx` has no mounted corpus control and `HomePage` has no file input; `ingestFile` has no non-test UI caller. The new plan restores the standalone home entry. The current `POST /api/corpus/ingest` parses, chunks, and pushes synchronously and does not persist the uploaded raw bytes. `IngestStateStore` is currently in-memory.
- **To persist after T1:** record the decided permanent-upload job and readiness vocabulary in the fin glossary/spec; coordinate the iknow job's public states through the sibling plan. Do not mark these terms settled before the decision ticket.
- **Scope cut:** no automatic promotion of an attachment into the company corpus, no upload action on the thread composer, no corpus delete UI in this increment, and no change to retrieve ranking. Failed-submission object cleanup and version-replacement invalidation remain in scope.

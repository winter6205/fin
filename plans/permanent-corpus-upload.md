# Plan: permanent corpus upload and indexing

**Goal:** An operator can upload a supported source outside a research thread; fin durably stores the original, asynchronously parses and chunks it, pushes retrievable units, and tracks iknow-memory graph indexing as a separate job.
**Approach:** Restore a visible upload entry on the workspace home, then turn the synchronous ingest endpoint into a durable job whose raw-object, parse, chunk, and push stages can resume after restart. PDF parsing reuses the shared `fin.corpus.parsers` page/region core delivered by thread-attachment T2d; fin keeps ownership of deterministic chunking, while iknow-memory owns its separately queued graph-index job. A successful push is not reported as graph-index readiness.
**Spec links:** [`specs/corpus-serve-ingest.md`](../specs/corpus-serve-ingest.md), [`specs/corpus-ops-depth.md`](../specs/corpus-ops-depth.md), [`specs/thread-attachment-source-read.md`](../specs/thread-attachment-source-read.md), [`specs/graph-index-standard-fast.md`](../specs/graph-index-standard-fast.md).
**Sibling plans:** thread PDF parser seam: [`thread-attachment-source-read.md`](thread-attachment-source-read.md) T2d; bounded company `read_source`: [`../../iknow-memory/plans/bounded-source-read.md`](../../iknow-memory/plans/bounded-source-read.md) T1 (merged); iknow graph-index orchestration: [`../../iknow-memory/plans/corpus-index-job-orchestration.md`](../../iknow-memory/plans/corpus-index-job-orchestration.md) and its pinned contract [`../../iknow-memory/specs/corpus-index-job-orchestration.md`](../../iknow-memory/specs/corpus-index-job-orchestration.md). ## Settled contract and open seams

- **Inherits:** ADR 0047 keeps thread attachment and permanent corpus ingest as separate doors; ADR 0037 and `specs/corpus-retrieval.md` keep parsing and deterministic chunking in fin; ADR 0043 keeps raw bytes in the object store and metadata/pointers in fin; ADR 0069 runs entity descriptions from the iknow extract/index job, not from push or query.
- **Inherits:** the company source locator remains `{document_id, version, unit}`; pushed chunks carry the canonical `source_ref`; exact company-unit reads use iknow-memory's bounded `read_source` contract. iknow distinguishes per-source text-search readiness from corpus-wide graph/C readiness. No model-supplied path or thread id widens access.
- **Inherits:** iknow-memory `plans/bounded-source-read.md` T1 is merged and remains complete; this plan consumes its bounded exact-`source_ref` read contract without reopening it.
- **Settled by T1 (2026-09-25) — contract pinned in [`../specs/corpus-serve-ingest.md`](../specs/corpus-serve-ingest.md) (amendment 2026-09-25); the iknow half is pinned in [`../../iknow-memory/specs/corpus-index-job-orchestration.md`](../../iknow-memory/specs/corpus-index-job-orchestration.md):**
  - **Accept time point and accepted-response/job identity** — `POST /api/corpus/ingest` is accept-and-persist: it returns `job_id` only after raw bytes (object-store PUT) + pointer + `pending` job record + stable source identity (`document_id` + `version`) are durable, then parse / 切分 / push run asynchronously — spec "Accept time point" and "Synchronous endpoint retirement".
  - **`document_id` derivation** — `document_id = "{TICKER}-{FYQ}"` from a required `company` + `period` (upper-cased/normalized); an explicit `document_id` (for example an EDGAR accession) wins; the filename is metadata only and a filename-stem fallback is prohibited; missing both yields typed `document_id_missing` — spec "Decision 1 — stable `document_id` derivation".
  - **`content_identity` authority and fin's job-identity pair** — iknow-memory computes `content_identity` over the whole pushed body, stores it in a first-class unique column (jointly with `source_ref`), and returns it in the push response; fin puts no identity field on the wire (strict envelope), reads that stored value as its only authoritative `content_identity`, and keeps local `body_content_id` as bookkeeping only; fin's idempotency pair is `(source_ref, content_identity)` — spec "Decision 2 — `content_identity` authority and fin's job-identity pair" (amended 2026-09-26) and sibling plan/spec `corpus-index-job-orchestration`.
  - **Durable submission states and retry semantics** — the existing seven `IngestState` values are reused; the queued job state is `pending`; no `queued` / `running` / `stale` is introduced; a `failed` job retries from `fetching` without re-upload — spec "Decision 3 — fin job states (seven-state vocabulary, reused)".
  - **Finite upload-size cap** — the existing 50 MiB is retained, written exactly as `52428800` bytes; exact-cap (declared or streamed) is accepted, one byte over is typed `ingest_upload_too_large` — spec "Upload-size cap".
  - **Unsupported-format staging** — an unknown format / unspecified format / invalid `doc_type` / missing identity / over-cap is rejected **before** acceptance and persists nothing; a recognized-format parse, OCR, empty-extraction, or push failure is a typed `failed` job result **after** acceptance — spec "format / doc_type validation staging (explicit decision)".
  - **Duplicate / replacement / concurrent semantics** — the same `(document_id, version)` idempotently joins one job and returns the same `job_id`; a different version with no in-flight job is a replacement that invalidates stale chunks; a different version during an in-flight job is typed `concurrent_run`; no path yields two logical source versions — spec "Duplicate and concurrent submission".
  - **Per-source text readiness versus corpus-wide graph/C readiness** — `ready` means per-source **text** readiness only; no fin API claims graph/C readiness from a successful push, and graph/C is a separate pass-through field defined by the iknow index-job contract — spec "Graph/C readiness".
  - **Status polling contract** — the HTTP gate is wired to `IngestStateStore` and `GET` returns the real persisted state (never a constant `"ingested"` / `"accepted"`), `error_type` / `error_message` when `failed`, the per-source text-readiness flag, and a separate graph/C sub-object; an unknown id is typed `unknown_job` — spec "Status polling contract".
- **Still open:** none — every item previously listed under "Open for T1" is settled above. **Since T1 closed, the `corpus-serve-ingest` spec's synchronous endpoint contract is retired and the spec carries the amendment described above; the implementation itself remains T2–T4 work.**
- **Current runtime gap after fin that pull request (T2 partial):** the standalone home upload control, accept/status HTTP surface, raw-object/pointer submission path, and persisted-state polling UI are present. T2 is not complete: `ingest_state_store_from_env` still always returns `InMemoryIngestStateStore`; missing object-store or metadata configuration falls back to process memory while still accepting the upload; a different version of a ready source returns `replacement_unsupported` instead of performing the settled replacement/invalidation behavior. The parser/chunker/pusher worker remains T3 scope.
- **Cross-repository integration repair — delivered:** iknow-memory that pull request computes and stores `content_identity` during `push`, returns it in the push response, and validates that stored value at `submit_index_job`; its push schema rejects a caller-supplied identity on the single-envelope arm and ignores unknown keys inside an `items[]` batch item, so fin itself guarantees that no identity goes out on the wire. This PR closes the two remaining gaps: (a) the fin wording is corrected by the 2026-09-26 amendment to [`../specs/corpus-serve-ingest.md`](../specs/corpus-serve-ingest.md) Decision 2, so the single authoritative `content_identity` is the stored value read back from the push response and local `body_content_id` is fin-side bookkeeping only; (b) the fin push adapter now exposes that returned identity to its caller for the `(source_ref, content_identity)` idempotency pair. fin still must not independently recompute an identity at T4. **Real fin-to-iknow push coverage is delivered in this PR**, not deferred to T4: the opt-in driver `uv run pytest -q -m mcp tests/retrieve/test_live_content_identity.py` spawns the real stdio server against real PostgreSQL and asserts (1) that the identity the adapter exposes equals the value stored in `source_documents.content_identity` byte for byte, (2) that a re-push keeps the identity, the chunk ids and the row counts, and (3) that `submit_index_job` accepts that pair and refuses a different value by name — 5 passing cases at delivery.
- **Persisted with T1 (2026-09-25):** the decided permanent-upload job and readiness vocabulary live in the `corpus-serve-ingest` spec amendment; the iknow job's public states are pinned by the sibling iknow spec. Remaining propagation is the spec's own `待写入` list (a new ADR and the CONTEXT glossary entries), tracked there, not re-decided here.
- **Scope cut:** no automatic promotion of an attachment into the company corpus, no upload action on the thread composer, no corpus delete UI in this increment, and no change to retrieve ranking. Failed-submission object cleanup and version-replacement invalidation remain in scope.

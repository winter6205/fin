# Plan: Question Source Scope Completion

**Tracker:** [#405](https://github.com/oocang/fin/issues/405). This issue contains the complete plan; task labels are internal to this plan.
**Goal:** Close the remaining source-scope gaps from [PR #395](https://github.com/oocang/fin/pull/395) while keeping the approved source contract and #392 v1.0 behavior intact.
**Approach:** Materialize the approved #392 acceptance assets once, settle the current-authority and operation-capability facts, then enforce and verify the effective selection at existing source seams. Keep the Source Scope interface small: callers provide accepted intent, trusted current authority, and an operation; the module resolves one effective selection and returns a typed decision before an adapter reads data. This concentrates the policy behind the existing host seam without adding an authorization system, a second classifier, or a new acceptance contract.
**Spec link:** `specs/question-source-scope.md`
**Related plans:** [Runtime completion](question-task-runtime-completion.md) consumes the #392 assets materialized in this plan's T1. The original [Runtime plan](question-task-runtime.md) owns the shared scope representation in its T1 and the final integrated #392 gate.
**Dependencies:** Before any `src/` implementation, resolve [#400](https://github.com/oocang/fin/issues/400) independently and prove that a clean default `uv sync` checkout passes the existing staged typecheck and pre-commit/CI path. That separate issue owns its tooling diff and verification; no `uv.lock` edit is expected because the declared extras are already pinned. The original Runtime T1 shared-contract decision remains the prerequisite for Source Scope implementation.
**Per-ticket loop (implementation bullets):** tdd → relevant typecheck/tests → verification-before-completion.
**Persist list:** empty. No new domain term or ADR decision is proposed.

2. **Resolve what proves current operator permission** — tag: `[decision]`
   - **Inherits:** Source Scope decision 4: “A saved restriction is not an authorization grant. The host rechecks actual current permission, trusted thread ownership, source identity/version, readiness where relevant, operation capability, and applicable execution limits before every source path and evidence admission.” [Issue #234](https://github.com/oocang/fin/issues/234) says: “fin remains one operator per product.”
   - **Surface:** Existing host-agent authority facts, trusted thread/attachment ownership, shared corpus access, and the related [#401](https://github.com/oocang/fin/issues/401), [#163](https://github.com/oocang/fin/issues/163), and [#167](https://github.com/oocang/fin/issues/167) decisions.
   - **Acceptance:** The decision identifies the existing trusted fact, if any, that establishes the single product operator’s current permission for the company corpus and current-thread attachments, and records whether #163 or #167 already owns any part of that decision. Thread binding, readiness, collection health, and attachment identity/version are not treated as operator permission by themselves. The decision maps an absent grant to denial and an inability to consult current authority to dependency failure using existing typed outcomes. No new identity, RBAC, tenant, provider, or permission store is introduced. If the existing facts cannot establish a current grant or the existing outcomes cannot represent the result, the permission-recheck implementation remains blocked and the unresolved product decision returns to the operator; absence of evidence is never allow-all.
   - **Headroom:** The decision settles the fact and its failure meaning without prescribing a new authority object or storage layout.
   - **Decision:** Current permission is proved only by facts the host already trusts and the model cannot supply: the host-bound `thread_id` read from the run's `configurable`, plus the attachment store's own answers for the ids in question (`resolve_attachment` identity/version, `attachment_ready`, `list_attachments`). No new authorization provider, identity system, tenant boundary, store, or permission service was required, so the spec's return-to-operator condition is not triggered. An absent grant maps to denial; an inability to consult current authority maps to dependency failure — two distinct outcomes, never allow-all and never a truthful `empty`. For the company branch there is no separate grant to consult: with one operator per product (#234) the corpus is the shared access the host already has, so `EffectiveScope.company_allowed` plus proven expressibility is the whole ruling and no per-document ACL was invented.
   - **Evidence:** `src/fin/host/graph.py:_bound_thread_id` (the thread is a `configurable`-only host fact with no fallback and never a model argument); `graph.py:_scope_authority` (facts built from the frame's own store; a foreign-thread, tombstoned, unknown, or re-prepared id answers `None`, which is a denial, not a widening); `source_scope.py:AuthorityFacts` (every callable is required with no default, so an incomplete fact set is a construction error rather than a silent grant); `source_scope.py:resolve_scope` + `EffectiveScope.resolution_fault` (a raising read contributes nothing and records the fault type instead of an answered "nothing"); `source_scope.py:ScopeGate._check_broad` and `_check_attachment` (the fault is answered `SCOPE_DEPENDENCY_FAILED` ahead of both `SCOPE_SELECTION_EMPTY` and any denial code); `source_scope.py:_supported_ids` / `_default_ids` (eligibility only — readiness is deliberately not consulted, so an authorized-but-not-ready id stays in scope and earns `unavailable`).
   - **Two absent-authority cases are distinct, by design:** `graph.py:_authority_or_absent` returns `None` — no gate is constructed and each boundary keeps its pre-scope behavior byte for byte — only when nothing is in force (`ScopeRestriction.in_force`); a restriction in force over an absent store gets `graph.py:_absent_authority`, whose source reads all raise so the attachment branch resolves to a fault and is enforced as `dependency_failed` rather than released into the pre-scope broad path. Capability is deliberately not one of those raising reads, so an absent attachment store does not fake an outage for the company branch.
   - **Branch denial:** an operator-declared exclusive restriction (`ScopeRestriction.company_excluded`) removes the company branch; `ScopeGate._check_company` answers `SCOPE_COMPANY_NOT_PERMITTED` and orders that ruling **before** any capability question, so an adapter's health can never relabel a denial. `KnownLimit.remedy` from `ScopeGate._known_limits` carries the operator action that clears it, and `graph.py:_company_scope_refusal` applies the same decision to company boundaries that carry no per-run config. A restriction that merely names attachments leaves the branch eligible (ADR 0088:10).
   - **Consequences:** #401's missing-service bypass is closed **at the seam**, without inventing an authority model: a restriction in force over an absent authority is now enforced as a dependency failure instead of released into the pre-scope broad path. That closure is reachable only while a restriction is in force, and no production caller puts one in force yet — `scope_restriction` is passed by no composition root, and accepting and persisting it is Runtime's per decision 9. The bypass is therefore closed for the run that is handed a restriction, not for the shipped product surface. Thread binding, readiness, collection health, and attachment identity/version remain non-grants (decisions 1 and 7); permission, thread ownership, identity/version, readiness, and capability are re-read at each boundary rather than cached from resolution. A model-supplied id can never reach an authoritative check.
   - **Open:** Nothing product-level. Any realization beyond the existing store's per-thread ownership — a new ACL system, a second authority source, or a multi-operator model — is a new authorization system and must return to the operator first; current wiring does not need one. #163 and #167 own the attachment store and thread-ownership facts this decision consumes and are not reopened here.
   - [parallel]
   - Status: [x] done — decision settled on the evidence above; the enforcement bullets land under T4.

3. **Define restriction expressibility separately from source availability** — tag: `[decision]`
   - **Inherits:** Source Scope decision 5: “An operation that cannot express the approved restriction reports unsupported before returning source data.” Decision 7 keeps permission denial, unsupported or unavailable capability, dependency failure, and successful-empty distinct. This resolves the capability reachability gap tracked by [#402](https://github.com/oocang/fin/issues/402).
   - **Surface:** Existing host Source Scope checks, the neutral retrieve port, current corpus and attachment adapters, and named source failures.
   - **Acceptance:** The decision maps each current source operation to the adapter fact that proves it can express the approved restriction before data is returned. An adapter’s inability to express a restriction maps to the existing typed `unsupported` outcome; an unconfigured or unhealthy deployment, not-ready attachment, and successful-empty result retain their existing distinct outcomes. A general registry is introduced only if discovery shows multiple real adapters with independently varying capability maps; a hypothetical mapping is not sufficient. If no current operation can produce a truthful `unsupported` result, record that fact and keep #402 / SC-4 unaccepted rather than representing an outage as unsupported.
   - **Headroom:** The decision freezes the observable capability contract and ownership, not a registry shape, enum, or new failure vocabulary.
   - **Decision:** Expressibility and availability are two different facts and keep two different codes. **Expressibility** is whether a wired adapter can carry the approved narrowing at all: membership in the closed `SCOPE_EXPRESSIBLE_OPERATIONS` set. **Availability** is whether it can answer right now: readiness and transport health, reported as `unavailable` or `dependency_failed`, with readiness never acting as a permission grant. `unsupported` is reachable only through inexpressibility.
   - **Evidence:** `source_scope.py:SCOPE_EXPRESSIBLE_OPERATIONS` (a discovery result, each member named for the seam that proves it: `search_attachments` takes an id narrowing via `attachment_retrieval.AttachmentSearchPort.search` (implemented by `ThreadAttachmentRetriever`); `search_corpus` and `list_files` read the corpus the branch decision governs; `read_source` and `read_visual_detail` take one named locator; `admit_evidence` is host-side; `get_xbrl_fact` and `compare_facts` name one document; `COMPANY_CAPABILITY` is the branch token in a report); `source_scope.py:ScopeGate._capability_decision` (the set is consulted **inside** the gate before the host probe is asked, so no host-supplied callable can open an operation nothing proves, and a probe that raises is `SCOPE_DEPENDENCY_FAILED` rather than an assumed grant); `graph.py:_adapter_capability` (derived membership, which replaced the unconditional `return True` that `_scope_authority` previously wired as `operation_capable`); `source_scope.py:ScopeGate._check_attachment` (an in-scope, authorized, not-ready id answers `unavailable` / `SCOPE_ATTACHMENT_NOT_READY`); `fin/retrieve/tiers.py:TIER_NOT_OPEN` and `REAL_DB_NOT_WIRED` remain the authority for deployment and service health.
   - **Consequences:** The direction of failure flipped: an operation added without proving its adapter expresses the narrowing now fails closed as `unsupported` before any source data, instead of open as permitted — proven at module level by `tests/host/test_source_scope.py:test_an_operation_with_no_expressing_adapter_is_unsupported`, with `test_every_wired_operation_is_declared_expressible` pinning the current membership. Because the wired probe and the gate consult the same set, the probe can only agree, so no availability fact can produce `unsupported` and the four decision-7 outcomes stay collapsible-free. No general capability registry was introduced: the closed set is enough because no two real adapters vary capability independently, and ADR 0039's rule that the product seam carries no capability parameter is unchanged.
   - **Open — the honest consequence for T5 / #402:** Every currently wired operation is proven expressible, so no end-to-end `unsupported` journey can be produced from real wiring today. T5 therefore remains blocked and is not marked done; spec SC-4 is only partially evidenced and #402 stays unaccepted. The module-level inexpressibility check is evidence of the rule, not of the journey — decision 10 keeps module-level evidence from substituting for the #392 integrated gate, and T5's own bullet forbids an out-of-band unit-only gate drive. Should a future adapter genuinely fail to express the narrowing, that refusal becomes reachable and T5 can be run against it. **What this decision does NOT yet evidence:** the wired probe and the gate consult the same closed set, so today `unsupported` answers an operation NAME that is not listed, never a listed operation whose adapter has stopped carrying the narrowing. No wired seam supplies that adapter fact, so T5's adapter-incapacity requirement is unevidenced rather than implemented; closing it needs a probe that answers from the cited seams themselves (`AttachmentSearchPort.search`, the locator-taking readers), which is a named follow-up outside this plan. The comment that previously named a nonexistent `AttachmentRetriever` now names `AttachmentSearchPort.search`, which exists and takes `attachment_ids`.

## ADR 0088 interpretation

This plan preserves the accepted distinction between explicitly restricting a source set and merely naming an attachment. J03’s “Use only the attached A1 policy” is an explicit restriction; a bare mention of A1 does not exclude company material, especially when the same question asks for it. This does not reopen ADR 0088. An implementation that misses the distinction is a defect to fix under the existing contract; reopen ADR 0088 only if independent evidence shows its accepted rule itself cannot coexist with J03's explicit restriction.

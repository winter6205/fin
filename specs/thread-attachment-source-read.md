# Spec: thread attachment retrieval and bounded source reads

> **Status:** G4 contract. Product decisions were confirmed in the operator's 2026-09-24 G4 interview; inherited runtime constraints are identified below. Implementation has not started. This spec spans fin and the company-source `read_source` wire in iknow-memory. Implementation plans belong in their respective repositories.

## Objective

Let an operator attach text, PDF, or image material to a research thread and use it as searchable, citable evidence across turns. Fin owns each thread's attachment source and index; company material remains in iknow-memory. A grounded run can discover eligible sources with `retrieve` and inspect one known source unit with `read_source`, receiving bounded text and an explicit continuation position.

The operator can ask about a named attachment, all ready attachments in the current thread, company material, or a comparison of an attachment with company material. No attachment from another thread can enter retrieval, reads, or citation evidence.

## Confirmed decisions and inherited assumptions

1. The current product is the existing single-operator **工作台**. G4 isolates tool access between research threads and does not add user accounts or a multi-user authorization model. The host, rather than a model-supplied argument, supplies the active thread to tools (ADR 0088). Current no-auth HTTP access is a separate deployment boundary: a client allowed to choose another thread URL is not an unauthorized user in this contract.
2. The existing binary attachment door and separate corpus-ingest door remain distinct. Uploading an attachment never adds it to the permanent company corpus (ADRs 0047 and 0083).
3. Fin owns durable attachment bytes, parsed source text, metadata, and the thread-private searchable index. The index is derived from the parsed text; process restart must recover source and restore index availability before `ready` is reported (ADR 0088).
4. Host rules classify `text`, `pdf-text`, `pdf-scanned`, `image`, or `unsupported`. Parsing and indexing begin asynchronously after upload; `ready` means both text and index are usable (ADRs 0084 and 0086).
5. `read_source` replaces the model-facing `read_file`. Company and attachment locators are distinct typed identities using `unit`; no compatibility contract for generic `page` is retained (ADRs 0087 and 0088).
6. A source read returns at most 8,000 Unicode code points of one frozen unit and a complete serialized result of at most 32 KiB. Continuation is a zero-based Unicode-code-point position, initially zero, carried separately from the locator; both the backend wire and model-facing result are bounded (ADR 0088).
7. Ready attachments in the active thread and authorized company material are eligible by default. Naming an attachment narrows only the attachment branch; an explicit company-material request keeps the company branch eligible (ADR 0088).
8. Evidence and citations use only source text returned in the current run. A known valid locator can be read directly without a same-run retrieval hit (ADRs 0046 and 0087).

## Boundaries

- **Does:**
  - Accept binary files through the existing thread attachment API, assign a logical `attachment_id`, and bind every attachment record and index entry to its owning `thread_id`. Store raw bytes and parsed units durably under fin ownership; remove them and derived index entries when the thread is deleted. The model receives no filesystem or object-store path.
  - Classify once from file bytes and PDF text-layer properties. Reject `unsupported` with `attachment_type_unsupported`. Run parse and index asynchronously after storage; expose `parsing`, `ready`, and `failed`, a named failure reason, and retry for failed processing. A process restart resumes or rebuilds incomplete work and does not report stale `ready` before the index is usable.
  - Use the same parsed, versioned frozen-unit text for attachment retrieval and reads. Attachment search is scoped by the host to the active thread; it remains reusable across turns and cannot be queried with a model-supplied thread override. Ready attachment hits carry `source_ref={kind:"attachment",attachment_id,version,unit}`. `unit` is a one-based frozen-unit ordinal; read `position` is a separate zero-based offset within that unit.
  - Preserve company retrieval behind the existing retrieve port and iknow-memory. Company hits and reads use `source_ref={document_id,version,unit}`. The host combines eligible source branches without moving company ranking or attachment data into the other repository.
  - Apply attachment selection per question: an explicitly named attachment limits attachment candidates to that ID; a simultaneous explicit company request still searches company sources. A question requiring a named attachment that is still `parsing` exits as `attachment_not_ready`; unrelated questions can use ready sources.
  - Expose one model-facing `read_source({source_ref, position?})`. `position` defaults to zero. Resolve exactly one frozen unit at the locator's version; return its contiguous text slice, the same `source_ref`, and `next_position` (or `null` at end). A non-final successful slice advances the position. A known valid locator needs no same-run retrieve hit.
  - Enforce the 8,000-code-point text maximum and 32-KiB UTF-8 serialized-result maximum before company text leaves iknow-memory and before attachment text leaves fin's read boundary. The 32-KiB measure includes the complete JSON MCP tool result object for company reads and the complete JSON tool-result content for the model for both source kinds; it excludes transport-controlled JSON-RPC framing and model-generated tool-call IDs. Fin rejects an oversized backend result and bounds its own result. A `position` is measured in Unicode code points, not UTF-16 code units, UTF-8 bytes, tokens, lines, or PDF pages. Oversized locator metadata fails with a typed invalid-locator result rather than producing an oversized response.
  - Migrate retrieval locators, read contracts, evidence records, citation DTOs, and web citation display from generic `page` to `unit`. The PDF presentation may label a physical unit as a page; non-PDF units are displayed as units. Remove the old `read_file` model tool and old `page` locator contract without a compatibility layer.
  - Admit only text actually returned by `retrieve` or `read_source` in the current run to the citation verifier. Adjacent read slices of the same versioned unit may form one contiguous evidence span only when every code point between their positions was returned in that run; no unseen gap may be bridged. Validate attachment identity, active-thread ownership, and parsed-content version before a read or citation can succeed. Cross-thread and unknown identities share `unknown_locator` behavior and reveal no source text. Show the attachment's safe display filename in citations while retaining its logical ID as the identity.
  - Provide typed, observable exits for unsupported type (`attachment_type_unsupported`), empty parsed text (`attachment_empty_text`), parsing/index failure (`render_failed`, `vision_call_failed`, `vision_empty_text`, or `attachment_index_unavailable` where applicable), required attachment not ready (`attachment_not_ready`), invalid read position (`invalid_position`), invalid/oversized locator metadata (`invalid_locator`), unknown locator/version (`unknown_locator`), backend transport/storage outage (`source_unavailable`), and malformed or oversized backend responses (`source_backend_contract_error`). These are structured result/error codes, never inferred from prose. A failed index is never represented as an empty successful retrieval or `ready` attachment. Implementation documents each fallback/early return with an `EXIT` comment in the source language; it neither swallows exceptions nor silently retries against another source.
  - Add a committed, versioned G4 gold set using representative attachment bytes and existing company-source gold data. Exercise the real fin thread store, object store, and live iknow-memory MCP/store path, plus the live vision/model path for cases whose outcome depends on those providers. Compare actual source identities, text slices, statuses, answer evidence, and citations with independently stated expectations; save per-case real output and commands before claiming G4 completion. Fixture-server MCP and scripted/Fake model tests remain contract tests, not the real-gold result.
- **Confirms with human:** none remaining for the G4 product contract. Physical table layout, derived-index engine, and parser adapter placement are implementation choices constrained by the outcomes above.
- **Out of this spec:** a multi-user identity system; permanent corpus ingest of attachments; new company ranking or four new host retrieve nodes; XBRL fact lookup; arbitrary path reads; a generic document browser; a replacement citation verifier; a compatibility path for `read_file` or generic `page`.

## Success Criteria

1. Default fin tests (`uv run pytest -q`) and affected web typecheck pass. An integration test uploads a binary attachment, observes `parsing` then `ready`, retrieves a matching unit in the same thread on a later turn, and reads it via its typed locator.
2. A restart test preserves an attachment's bytes and parsed version and makes its index searchable again before the API reports `ready`. A failed or incomplete rebuild exposes a non-ready named state, not a successful empty hit set.
3. Deleting a thread removes its attachment metadata, raw bytes, parsed units, and derived index entries. Deletion racing with parsing cannot recreate an index entry or restore `ready`; cleanup failure is observable and retriable rather than acknowledged as complete. Reusing its old `attachment_id` yields `unknown_locator`; the permanent company corpus remains untouched.
4. A cross-thread test attempts retrieve and direct `read_source` using another thread's attachment ID and receives no hits or text. A model-supplied `thread_id` cannot change the host-bound scope.
5. An attachment named in a question narrows attachment hits to that ID. A question that names it and asks for company material also returns eligible company hits. A question requiring a still-parsing named attachment yields `attachment_not_ready`, while an unrelated question can use ready sources.
6. Text/PDF-text/scanned-PDF/image fixtures take the classified parsing path; unsupported bytes return `attachment_type_unsupported`. Render failure, vision-call failure, and empty vision text produce their respective named failed states; retry can transition a failed attachment to `ready` after successful reprocessing.
7. A company-source and an attachment-source unit longer than 8,000 code points can each be read in successive calls. Every returned text slice has at most 8,000 code points, the complete serialized backend tool result and model-facing result content are each at most 32 KiB in UTF-8, `next_position` strictly advances until `null`, and concatenated slices reproduce the unit text exactly. Include supplementary-plane Unicode and escaping-heavy text in the contract tests.
8. The iknow-memory `read_source` response is bounded before MCP transport serialization. The fin adapter maps an oversized or malformed backend result to `source_backend_contract_error` and a transport exception to `source_unavailable`, without passing text to the model; fin's attachment read applies the same response bounds. An index outage maps to `attachment_index_unavailable`, not an empty successful hit set.
9. Invalid, negative, non-integral, and beyond-end positions have typed failure behavior; unknown IDs, stale versions, and cross-thread attachments return `unknown_locator`. A valid direct locator read succeeds without a prior retrieve call in that run.
10. A grounded answer quoting only the first slice cannot cite text present solely in an unread later slice. A quote spanning two adjacent returned slices of one unit can pass; the same quote fails when a gap was not returned. A citation carrying another thread's attachment ID or a stale parsed version fails even if the quote text matches. A quote from a returned attachment or company unit produces a `unit` citation in API and UI. Attachment citations show a safe display filename; non-PDF citations are not labeled as PDF pages.
11. The model-visible tool list contains `read_source` and no `read_file`; generated locators and citation DTOs contain `unit` and no generic `page`. Contract tests cover empty, invalid, overflow, concurrent, and backend-exception input classes at the public entry points, including concurrent retry of one attachment without duplicate active index versions.
12. A committed G4 gold set covers text, PDF-text, scanned PDF, image, long Unicode continuation, same-thread follow-up/restart, cross-thread denial, and attachment/company comparison using the existing company-source gold corpus where relevant. Its real-service run records each case's expected and actual status, source identity, evidence/citation outcome, and pass/fail, plus the command, dependency configuration, dataset version, and measured read bounds. A missing live dependency is recorded as blocked, never as a green skip or a substitute Fake pass.

## Inherits / Changes

Quoted from [`docs/CONTEXT.md`](../docs/CONTEXT.md) (exact copy):

- **thread attach**: "An operator-submitted file under a logical `attachment_id` for the **research thread** lifetime; fin owns its durable bytes, parsed units, thread-private searchable index, and `parsing`/`ready`/`failed` state. `ready` requires a usable index, including after restart; the host binds access to the active thread, deletion removes its attachment data, and attaching never pushes it into the permanent company corpus (ADRs 0083, 0085, 0086, and 0088)."
- **read_source**: "The selected model-facing name for a known-locator source read, currently exposed in code as `read_file`: it resolves one authorized source unit from the company corpus or active-thread attachment without requiring a `retrieve` hit in the same run. Each read returns at most 8,000 Unicode code points and a complete serialized response of at most 32 KiB, including on the backend wire; continuation uses a zero-based code-point `next_position`, and only text returned in this run may become citation evidence (ADRs 0046 and 0088)."
- **locator**: A typed source identity for citation and `read_source`: company sources use `{document_id, version, unit}` and thread attachments use `{kind: "attachment", attachment_id, version, unit}`. The host validates the attachment against the trusted active thread and parsed-content version; a read continuation position is separate from the locator. Retrieved chunks carry a locator as `source_ref`, while the claimed quote remains separate (ADRs 0046 and 0088).
- **冻结单元**: A versioned, locator-addressed unit of parsed source text that fin determines before retrieval chunking; "frozen" means its text is fixed for that parsed version, not that fin creates a cache or separate persistence tier. Search chunks are contiguous substrings of the unit, while citation evidence comes only from text returned by `retrieve` or `read_source` in the current run (ADR 0046).

**Inherits:** ADRs 0046/0047 and 0083–0088; the existing fin thread store, object-store port, attachment HTTP door, retrieve port, citation verifier, and web citation surface; iknow-memory's company `read_source` source-document store. The current attachment upload is text-only, process-local, and one-use; this contract replaces that behavior.

**Changes:** fin gains durable thread-owned attachment preparation, search, deletion, and typed source reads; iknow-memory gains bounded company source-read wire; all generic `page` locator and citation fields become `unit` across the active product path.

**Planned capability allocation:** fin's attachment capability owns raw-byte references, parsed frozen units, index, state, retry, and deletion through a thread-bound interface. The existing object-store port supplies bytes and gains deletion support; workspace HTTP handles request/response only. The retrieve capability composes company and thread-attachment candidates through source-specific adapters without duplicating company ranking or moving attachment text to iknow-memory. Host tools validate typed locators and bind active-thread scope; the citation gate handles returned evidence spans; API DTOs and web components render `unit` citations. In iknow-memory, the source-read tool owns input/output validation and code-point slicing before MCP response assembly, while storage remains the company source-document authority. No parsing, indexing, or slicing is embedded in the HTTP route or graph node.

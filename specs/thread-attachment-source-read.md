# Spec: thread attachment retrieval and bounded source reads

> **Status:** G4 contract. Product decisions were confirmed in the operator's 2026-09-24 and 2026-09-25 G4 discussions; inherited runtime constraints are identified below. T2a–T2f implementation has not started. This spec spans fin and the company-source `read_source` wire in iknow-memory. Implementation plans belong in their respective repositories.

## Objective

Let an operator attach text, PDF, or image material to a research thread and use it as searchable, citable evidence across turns. Fin owns each thread's attachment source and index; company material remains in iknow-memory. A grounded run can discover eligible sources with `retrieve` and inspect one known source unit with `read_source`, receiving bounded text and an explicit continuation position.

The operator can ask about a named attachment, all ready attachments in the current thread, company material, or a comparison of an attachment with company material. No attachment from another thread can enter retrieval, reads, or citation evidence.

## Confirmed decisions and inherited assumptions

1. The current product is the existing single-operator **工作台**. G4 isolates tool access between research threads and does not add user accounts or a multi-user authorization model. The host, rather than a model-supplied argument, supplies the active thread to tools (ADR 0088). Current no-auth HTTP access is a separate deployment boundary: a client allowed to choose another thread URL is not an unauthorized user in this contract.
2. The existing binary attachment door and separate corpus-ingest door remain distinct. Uploading an attachment never adds it to the permanent company corpus (ADRs 0047 and 0083).
3. Fin owns durable attachment bytes, parsed source text, visual derivatives, metadata, and the thread-private searchable index. The index is derived from parsed text and page/region visual observations; process restart must recover source and restore index availability before `ready` is reported (ADRs 0088 and 0089).
4. Upload stores the raw bytes only. A successful upload is `uploaded` and is ready to attach to a message; no document classification, OCR, layout analysis, vision call, or indexing runs at upload time. On the first grounded graph turn for which the attachment branch is eligible, the graph starts or reuses a durable parse job. `ready` means the text, visual derivatives, and thread-private index are usable. Parsing is asynchronous and resumes the same suspended run when complete. As recorded in ADR 0089, this T2 contract supersedes the upload-time parse start in ADR 0086 and ADR 0084's whole-file document-class dispatch; unsupported content fails during graph-triggered preparation. Jev remains outside document parsing.
5. `read_source` replaces the model-facing `read_file`. Company and attachment locators are distinct typed identities using `unit`; no compatibility contract for generic `page` is retained (ADRs 0087 and 0088).
6. A source read returns at most 8,000 Unicode code points of one frozen unit and a complete serialized result of at most 32 KiB. Continuation is a zero-based Unicode-code-point position, initially zero, carried separately from the locator; both the backend wire and model-facing result are bounded (ADR 0088).
7. Ready attachments in the active thread and authorized company material are eligible by default. Naming an attachment narrows only the attachment branch; an explicit company-material request keeps the company branch eligible (ADR 0088).
8. Text quotes use only source text returned in the current run. Visual claims use a separate typed evidence path: fin persists each versioned visual observation with provenance to the original attachment page/crop, and the current run must explicitly retrieve or read that evidence. A cached observation that exists only in model conversation memory is not evidence. Call the configured vision model again only when the question asks for visual detail the stored observation does not cover. A known valid locator can be read directly without a same-run retrieval hit (ADRs 0046, 0087, and 0089).

## Boundaries

- **Does:**
  - Accept binary files through the existing thread attachment API, assign a logical `attachment_id`, and bind every attachment record and index entry to its owning `thread_id`. Configure a finite maximum upload size in bytes per attachment; do not rely on the current HTTP route's 2 MiB hard limit or leave the limit unbounded. The repository plan must determine the initial default from the committed real-gold PDF/image sizes and target deployment capacity. An upload exceeding the configured maximum fails with `attachment_too_large`; reject it without leaving attachment metadata or a partial object, including when the limit is exceeded while streaming. The upload operation stores raw bytes only and reports `uploaded` after durable storage succeeds. Upload completion is distinct from parse/index readiness. While any attachment upload is in flight for the composer/thread, the send gate prevents starting or sending a conversation, even if the pending file is not referenced by the message. The host enforces the same condition; it accepts a stored `uploaded` attachment without waiting for parsing. The model receives no filesystem or object-store path.
  - Start attachment preparation only when an attachment is eligible for a grounded graph turn. After track classification and any pending choice window, the graph passes through the existing compaction gate, then an `ensure_attachment_ready` orchestration node before a model/retrieval leaf. That node resolves eligible attachments under the current thread scope, starts or joins a durable job keyed by attachment identity and raw-content version, and routes to the existing leaf when preparation is ready. The node does not parse, render, call OCR/vision, or build an index itself; it calls the fin-owned attachment capability. When preparation is pending, persist the run identity and wait state, release the thread execution lock, and resume the same run at the gate after completion. Do not ask the operator to resend the question. A restart recovers both the job and its waiting run without creating duplicate active jobs or duplicate turns.
  - Preserve graph order and branch behavior:

    ```mermaid
    flowchart TD
      A[classify] --> B{choice window pending?}
      B -- yes --> C[resolve choice, then classify]
      B -- no --> D[compaction_gate]
      C --> D
      D --> E{grounded attachment eligible?}
      E -- no --> F[existing non-research leaf or grounded model/tool loop]
      E -- yes --> G[ensure_attachment_ready]
      G -- ready --> H[grounded model and retrieve/read loop]
      G -- pending --> I[persist wait and release thread lock]
      I --> J[durable parse job completes]
      J --> G
      G -- failed or deleted --> K[typed exit]
      H --> L{visual claim?}
      L -- no --> M[citation gate]
      L -- yes --> N[retrieve/read persisted visual evidence]
      N --> O{stored observation covers question?}
      O -- yes --> M
      O -- no --> P[inspect stored original page or high-resolution crop]
      P --> Q[configured vision provider; persist new observation version]
      Q --> M
    ```

    `ensure_attachment_ready` is an orchestration point; the attachment capability owns parse-job execution. The current run must explicitly read the matching stored visual evidence; only a question detail absent from that observation triggers another call using the persisted original page/crop.
  - Expose `uploaded`, `parsing`, `ready`, and `failed` as separate attachment lifecycle states. `uploaded` means the original bytes are durable. `parsing` begins only after the graph has requested preparation. `ready` requires parsed page units, required visual derivatives, and the thread-private index to be usable. A process restart resumes or rebuilds incomplete work and does not report stale `ready` before all required products are usable. Unsupported content fails during preparation with `attachment_type_unsupported`; upload itself does not classify or reject based on parser suitability.
  - Use the initial fin parser configuration: Docling's standard PDF pipeline with the Heron layout model, Tesseract OCR on CPU for scanned text, and a vision-capable provider behind a fin vision port separate from the conversational model port. The vision port reuses `FIN_MODEL`, `FIN_BASE_URL`, and `FIN_API_KEY`; it introduces no separate vision model/credential settings. Heron first identifies text, table, and image/figure regions with coordinates. Then the configured vision model scans the rendered full-page image of every page to identify whether it contains charts and describe what they express, including charts Heron did not box. If a question requests details that a stored page observation does not cover, send a high-resolution crop of each relevant chart/region (or the full page if no reliable box exists) for detailed reading and persist a new observation version. Run Heron on the configured local model device. Do not load a local VLM or a separate picture-classification model in this configuration; do not hardcode a provider or model ID. Preserve native PDF text, layout regions, OCR text, rendered source-page images, and page/region coordinates. Process a mixed PDF by physical page and region rather than assigning one text/scanned label to the whole file. Persist page/region visual observations as derived search material, clearly distinguished from source text. Standalone images use the same OCR-plus-configured-vision path.
  - For a question whose answer uses visual content, the grounded path first explicitly retrieves/reads the candidate persisted observation into the current run. The grounded model then supplies structured `required_details` and requested scope from the question and current-run evidence; the host owns and deterministically evaluates sufficiency. Each observation persists `coverage_schema_version`, `observation_version`, attachment content version, source unit and physical page, original page-image hash, provider/model version, and `covered_details`, whose entries pair a structured detail key with the scope actually observed. Scope is either `whole_page` or a normalized bounding box in the original page-image coordinate space. A detail key has a stable `kind` and a complete `target_key`. For an exact plotted value, the target must identify the chart, series, and category (or an equivalent complete target path); a generic `plotted_value` facet does not cover every value in the chart. The host reuses an observation only when attachment version, unit/page, page-image hash, and supported coverage schema match; every required detail key exactly matches a covered key; and the observed scope contains the requested scope. The host performs no semantic or fuzzy matching. A missing/ambiguous target, missing field, unknown scope, unknown coverage schema, or any otherwise unknown detail is insufficient and triggers inspection of the stored original. Use a reliable relevant crop when target and region are known; otherwise inspect the full page. Multiple current-run observations may jointly cover a request only when each required detail has an exact key and containing scope match under the same source/version/hash checks. A current-run visual evidence token binds the returned observation set to its provenance and original location. This is a host-controlled image read through fin-owned bytes, not model-visible filesystem access.
  - Bound visual work explicitly. Each deployment must configure a finite maximum PDF page count per attachment and a finite visual-call budget per run; unbounded or missing limits fail startup/config validation. Exceeding the page cap fails preparation with `attachment_page_limit_exceeded`; exceeding the visual-call budget fails with `attachment_vision_budget_exceeded`. Fail before silently truncating any page or region. The first preparation performs one full-page vision scan per physical page, with pages submitted singly. At the current cap of 80 pages, reserve one run-wide full-page transport retry and allow at most eight question-specific crop calls: `80 + 8 + 1 = 89` maximum outbound attempts. The retry reserve is one per run, not one per page; only an adapter-classified retryable full-page transport failure may consume it. Non-retryable errors, malformed/empty results, and crop calls are not retried. Each outbound attempt, including a failed attempt, consumes one call. T2e must update the deployment example from 88 to 89 and enforce `page_cap + crop_cap + 1` in boot validation and run preflight; the decision record does not change runtime configuration. Crop calls remain a finite sub-allocation and cannot raise the total run cap. Record page count, full-page and crop calls, image dimensions, provider-reported usage/cost, latency, and retry count; mark cost unavailable if the provider does not report it. No per-turn monetary ceiling is part of T2e: usage and cost are recorded for a later budget decision, and there is no monetary preflight gate. A structured response saying that a page has no chart is a successful visual result; a non-retried provider failure or missing/malformed visual result fails preparation with `vision_call_failed` or `vision_empty_text`, respectively.
  - Represent each PDF physical page as one frozen text unit and retain the physical page number and region bounds as metadata; table and figure regions remain anchored under their page unit rather than becoming generic `unit` locators. Preserve each image attachment as its own source unit. Text returned from native extraction or OCR may support a quoted-text citation after it is returned in the current run. A model-generated visual observation is never presented as a verbatim quote. A visual claim must carry the attachment `source_ref`, physical page, region (or whole page when no reliable box exists), and a visual evidence token for the persisted, versioned observation with original-image provenance. The current run must retrieve or read the matching visual evidence; model memory alone does not qualify. If a question asks for details missing from that observation, call the configured vision provider on the stored original page/crop and persist a new observation version.
  - Use the same parsed, versioned frozen-unit text for attachment retrieval and reads. Attachment search is scoped by the host to the active thread; it remains reusable across turns and cannot be queried with a model-supplied thread override. Ready attachment hits carry `source_ref={kind:"attachment",attachment_id,version,unit}`. `unit` is a one-based frozen-unit ordinal; read `position` is a separate zero-based offset within that unit.
  - Preserve company retrieval behind the existing retrieve port and iknow-memory. Company hits and reads use `source_ref={document_id,version,unit}`. The host combines eligible source branches without moving company ranking or attachment data into the other repository.
  - Apply attachment selection per question: an explicitly named attachment limits attachment candidates to that ID; a simultaneous explicit company request still searches company sources. When an eligible attachment is `uploaded` or `parsing`, suspend the dependent run while its durable parse job completes and resume that same run automatically. Questions that do not make an attachment eligible proceed without triggering its preparation. Parse failure exits with its named typed failure; it is never converted into an empty successful retrieval or a request for the operator to resend.
  - Expose one model-facing `read_source({source_ref, position?})`. `position` defaults to zero. Resolve exactly one frozen unit at the locator's version; return its contiguous text slice, the same `source_ref`, and `next_position` (or `null` at end). A non-final successful slice advances the position. A known valid locator needs no same-run retrieve hit.
  - Enforce the 8,000-code-point text maximum and 32-KiB UTF-8 serialized-result maximum before company text leaves iknow-memory and before attachment text leaves fin's read boundary. The 32-KiB measure includes the complete JSON MCP tool result object for company reads and the complete JSON tool-result content for the model for both source kinds; it excludes transport-controlled JSON-RPC framing and model-generated tool-call IDs. Fin rejects an oversized backend result and bounds its own result. A `position` is measured in Unicode code points, not UTF-16 code units, UTF-8 bytes, tokens, lines, or PDF pages. Oversized locator metadata fails with a typed invalid-locator result rather than producing an oversized response.
  - Migrate retrieval locators, read contracts, evidence records, citation DTOs, and web citation display from generic `page` to `unit`. The PDF presentation may label a physical unit as a page; non-PDF units are displayed as units. Remove the old `read_file` model tool and old `page` locator contract without a compatibility layer.
  - Admit only text actually returned by `retrieve` or `read_source` in the current run to the quoted-text citation verifier. Adjacent read slices of the same versioned unit may form one contiguous evidence span only when every code point between their positions was returned in that run; no unseen gap may be bridged. Visual evidence is a separate typed citation path: require the current run to retrieve/read the visual observation, validate its versioned provenance to the original page/crop and attachment version, and display a link to that original location. A fresh vision result is admissible after its observation and provenance are persisted and returned to the current run. Never turn a generated visual description into a source quote. Validate attachment identity, active-thread ownership, and parsed-content version before a read or citation can succeed. Cross-thread and unknown identities share `unknown_locator` behavior and reveal no source text. Show the attachment's safe display filename in citations while retaining its logical ID as the identity.
  - Provide single-attachment deletion through the chip's `×` action. Deletion tombstones the attachment version before cleanup so new reads, retrieval, visual inspections, and waiting runs cannot use it. A delayed parser/vision result must fail its version/tombstone check and cannot recreate parsed units, index entries, or `ready`. Remove raw bytes and derived data; retain a tombstone until cleanup is confirmed. If cleanup fails, expose typed `attachment_cleanup_failed`, keep access blocked by the tombstone, and allow cleanup retry rather than claiming deletion is complete. Thread deletion applies the same invalidation rule to all its attachments.
  - Provide typed, observable exits for upload size exceeded (`attachment_too_large`), unsupported type (`attachment_type_unsupported`), empty parsed text (`attachment_empty_text`), page/call budget exceeded (`attachment_page_limit_exceeded`, `attachment_vision_budget_exceeded`), attachment deletion cleanup failure (`attachment_cleanup_failed`), parsing/index failure (`render_failed`, `vision_call_failed`, `vision_empty_text`, or `attachment_index_unavailable` where applicable), upload in progress (`attachment_upload_in_progress`), stale/deleted attachment (`unknown_locator`), invalid read position (`invalid_position`), invalid/oversized locator metadata (`invalid_locator`), unknown locator/version (`unknown_locator`), backend transport/storage outage (`source_unavailable`), and malformed or oversized backend responses (`source_backend_contract_error`). These are structured result/error codes, never inferred from prose. A failed parser, visual pass, or index is never represented as an empty successful retrieval or `ready` attachment. Implementation documents each fallback/early return with an `EXIT` comment in the source language; it neither swallows exceptions nor silently retries against another source.
  - Add a committed, versioned G4 gold set using representative mixed text-and-chart PDFs, scanned pages, standalone images, and existing company-source gold data. Exercise the real fin thread store and object store, the pinned Docling/Heron and Tesseract runtime, the configured vision provider, and the live iknow-memory MCP/store path for company-source cases. Compare actual page/region coverage, extracted text, OCR, visual evidence, source identities, lifecycle states, answer evidence, and citations with independently stated expectations. Save per-case real output, commands, parser/model artifact versions, dataset version, and resource measurements before claiming G4 completion. Fixture-server MCP and scripted/Fake model tests remain contract tests, not the real-gold result.
- **Confirms with human:** none remaining for the G4 product contract. Physical table layout, derived-index engine, and parser adapter placement are implementation choices constrained by the outcomes above.
- **Out of this spec:** a multi-user identity system; permanent corpus ingest of attachments; new company ranking or four new host retrieve nodes; XBRL fact lookup; arbitrary path reads; a generic document browser; a replacement citation verifier; a compatibility path for `read_file` or generic `page`.

## Success Criteria

1. Upload stores raw bytes only and returns `uploaded`; no parser or model provider is invoked by upload. A finite configured size cap accepts the committed real-gold PDF/image fixtures; an over-limit upload returns `attachment_too_large` and leaves neither a partial object nor attachment metadata. While any upload is in flight, neither the Composer nor the host send path starts/sends a conversation. After a grounded turn makes the attachment eligible, the graph starts/reuses preparation, exposes `parsing`, resumes the same run automatically, and then retrieves/reads a matching unit.
2. A restart test preserves raw bytes, page-level parsed/visual products, version, index, durable parse job, and suspended run; it resumes the same run after rebuilding and reports `ready` only when all required products are usable. A failed or incomplete rebuild exposes a typed non-ready state, not a successful empty hit set.
3. Deleting a thread or one attachment removes its metadata, raw bytes, parsed units, visual derivatives, and derived index entries. Deletion racing with parsing/vision cannot recreate an index entry or restore `ready`. Cleanup failure returns `attachment_cleanup_failed`, remains visible and retriable, and leaves the tombstone blocking all access until cleanup succeeds; it is never acknowledged as complete. Reusing the old `attachment_id`/version yields `unknown_locator`; the permanent company corpus remains untouched.
4. A cross-thread test attempts retrieve and direct `read_source` using another thread's attachment ID and receives no hits or text. A model-supplied `thread_id` cannot change the host-bound scope.
5. An attachment named in a question narrows attachment hits to that ID. A question that names it and asks for company material also returns eligible company hits. A grounded turn requiring an `uploaded` attachment waits for preparation and resumes without resubmission; a turn for which attachment sources are ineligible does not trigger parsing.
6. Text PDFs, mixed text-and-chart PDFs, scanned PDFs, and standalone images use the same page/region preparation contract; no whole-file `text` versus `scanned` label selects a separate product path. Heron identifies text/table/figure regions and coordinates, Tesseract extracts scanned text, and the configured fin vision model inspects every rendered full page for charts, including layout misses. Unsupported bytes fail during preparation with `attachment_type_unsupported`. Render failure, vision-call failure, malformed/empty vision output, page/call budget overflow, and empty parsed text produce their typed failures. A transport retry is attempted at most once per run for a retryable full-page call only; normal preparation retry can transition a failed attachment to `ready` after successful reprocessing.
7. A company-source and an attachment-source unit longer than 8,000 code points can each be read in successive calls. Every returned text slice has at most 8,000 code points, the complete serialized backend tool result and model-facing result content are each at most 32 KiB in UTF-8, `next_position` strictly advances until `null`, and concatenated slices reproduce the unit text exactly. Include supplementary-plane Unicode and escaping-heavy text in the contract tests.
8. The iknow-memory `read_source` response is bounded before MCP transport serialization. The fin adapter maps an oversized or malformed backend result to `source_backend_contract_error` and a transport exception to `source_unavailable`, without passing text to the model; fin's attachment read applies the same response bounds. An index outage maps to `attachment_index_unavailable`, not an empty successful hit set.
9. Invalid, negative, non-integral, and beyond-end positions have typed failure behavior; unknown IDs, stale versions, and cross-thread attachments return `unknown_locator`. A valid direct locator read succeeds without a prior retrieve call in that run.
10. A grounded answer quoting only the first slice cannot cite text present solely in an unread later slice. A quote spanning two adjacent returned slices of one unit can pass; the same quote fails when a gap was not returned. A citation carrying another thread's attachment ID or a stale parsed version fails even if the quote text matches. A quote from returned attachment/company text produces a `unit` citation. A visual citation points to the original attachment page and region; its evidence token proves that this run retrieved/read the matching persisted observation and that the observation's versioned provenance binds to the original image/crop. Reuse tests cover exact detail-key and scope matches, an absent detail, unknown/missing target and scope, and an unrelated plotted value that must not satisfy an exact chart/series/category request. A later turn can cite the stored observation without another vision call, but must retrieve/read it in that turn; if it asks for missing detail, the original is inspected and a new observation version is stored before citation. Attachment citations show a safe display filename; non-PDF citations are not labeled as PDF pages.
11. The model-visible tool list contains `read_source` and no `read_file`; generated locators and citation DTOs contain `unit` and no generic `page`. Contract tests cover empty, invalid, overflow, concurrent, and backend-exception input classes at the public entry points, concurrent retry of one attachment without duplicate active index versions, upload byte-size overflow with no partial persistence, global send blocking while an upload is in flight, and typed page/vision-budget overflow. At 80 pages and 8 crops, budget validation admits 89 attempts and rejects 88; all attempted calls count, only one retryable full-page transport error per run may retry, and non-retryable, malformed-result, or crop failures do not retry.
12. A committed G4 gold set covers mixed text/chart PDF, scanned PDF, standalone image, chart missed by a Heron region box, chart found by full-page vision scan, high-resolution question-specific crop, visual citation on the first turn and a later turn from persisted observations, a later query that requires a new observation version, long Unicode continuation, same-thread follow-up/restart, cross-thread denial, upload/send race, single-file delete/parse race, and attachment/company comparison using the existing company-source gold corpus where relevant. Its real-service run uses Docling/Heron, CPU Tesseract, the configured vision provider, fin thread/object stores, and live iknow-memory for company-source cases. It records each expected and actual status, page/region coverage, OCR text, visual observation and provenance versions, whether the current turn retrieved/read that evidence, source identity, citation outcome, command, provider/artifact versions, dataset version, page/call budgets, image dimensions, per-call and per-run provider-reported usage/cost (or cost unavailable), latency, and observed resource peak on the 4 GB target device. A missing live dependency is recorded as blocked, never as a green skip or a substitute Fake pass.

## Open Questions

The three T2e0 decisions tracked by [issue #308](https://github.com/oocang/fin/issues/308) are resolved in this spec and [`plans/thread-attachment-source-read.md`](../plans/thread-attachment-source-read.md): observation sufficiency is a deterministic host check of structured versioned coverage after current-run read; the run reserves one full-page transport retry and therefore needs 89 calls for 80 pages plus 8 crops; and a separate fin vision port reuses `FIN_MODEL`, `FIN_BASE_URL`, and `FIN_API_KEY`. A monetary ceiling is deliberately deferred and is not a T2e blocker; provider-reported usage/cost is recorded, with omitted cost marked unavailable. T2e still must implement the 89-call deployment setting and enforcement. Each deployment must have finite attachment upload-byte, PDF-page, and per-run vision-call budgets. Existing measured defaults remain subject to the limitations recorded in the T2a validation artifact; the 89-call enforcement and `.env.example` update are T2e implementation obligations, not delivered by this decision update. Fin may choose the durable storage schema details and derived-index engine within these constraints.

## Inherits / Changes

Quoted from [`docs/CONTEXT.md`](../docs/CONTEXT.md) (exact copy):

- **thread attach**: "An operator-submitted file under a logical `attachment_id` for the **research thread** lifetime; fin owns its durable raw bytes, parsed units, versioned **visual observations**, thread-private searchable index, and lifecycle state. `uploaded` means only that raw bytes are durable; an eligible graph turn starts or joins preparation, `ready` requires parsed text, required visual observations, and an index usable after restart, and the host binds access to the active thread, tombstones before cleanup, and never pushes the attachment into the permanent company corpus (ADRs 0083, 0085, 0086, 0088, and 0089)."
- **read_source**: "The model-facing name for a known-locator source read: it resolves one authorized source unit from the company corpus or active-thread attachment without requiring a `retrieve` hit in the same run. Each read returns at most 8,000 Unicode code points and a complete serialized response of at most 32 KiB, including on the backend wire; continuation uses a zero-based code-point `next_position`, and only text returned in this run may become quoted-text citation evidence (ADRs 0046 and 0088); visual claims use the separate **visual evidence** path (ADR 0089)."
- **attachment preparation job**: "Durable, idempotent work keyed by attachment content version that begins when an eligible grounded graph turn reaches `ensure_attachment_ready`; it performs layout, OCR, page rendering, full-page vision analysis, and indexing, then resumes the waiting run after completion, including after restart."
- **visual observation**: "A persisted, versioned description or structured result from fin's configured vision model inspecting an original attachment page or crop. It is derived search material tied to the attachment version and original image location, never source text or a verbatim quote (ADR 0089)."
- **visual evidence**: "A current-run reference proving that the run explicitly retrieved or read a matching persisted **visual observation**, with provenance to the original attachment version, source unit, physical page, and crop when available. A later run reads and reuses a sufficient stored observation without uploading the attachment again or repeating vision; a question needing detail absent from it triggers inspection of the stored original image and a new observation version (ADR 0089)."
- **locator**: A typed source identity for citation and `read_source`: company sources use `{document_id, version, unit}` and thread attachments use `{kind: "attachment", attachment_id, version, unit}`. The host validates the attachment against the trusted active thread and parsed-content version; a read continuation position is separate from the locator. Retrieved chunks carry a locator as `source_ref`, while the claimed quote remains separate (ADRs 0046 and 0088).
- **冻结单元**: A versioned, locator-addressed unit of parsed source text that fin determines before retrieval chunking; "frozen" means its text is fixed for that parsed version, not that fin creates a cache or separate persistence tier. Search chunks are contiguous substrings of the unit, while quoted-text citation evidence comes only from text returned by `retrieve` or `read_source` in the current run; visual evidence remains a separate page/region path (ADRs 0046 and 0089).

**Inherits:** ADRs 0046/0047 and 0083–0089; the existing fin thread store, object-store port, attachment HTTP door, retrieve port, citation verifier, and web citation surface; iknow-memory's company `read_source` source-document store. The T1 runtime currently accepts UTF-8 text only, stores attachments durably for their thread lifetime, and starts parsing after upload; ADR 0089 records the T2 raw-only upload, graph-triggered preparation, and PDF/image visual-evidence contract.

**Changes:** ADR 0089 records fin's raw-only upload with an `uploaded` state, graph-triggered durable preparation, page/region OCR and visual analysis, versioned visual observations with original-image provenance, current-run visual evidence, thread-private search, single-attachment deletion, and typed source reads. This spec carries the buildable contract; iknow-memory's bounded company source-read wire and the generic `page` to `unit` migration remain as specified in ADRs 0087 and 0088.

**Planned capability allocation:** fin's attachment capability owns raw-byte references, parse/vision jobs, parsed frozen units, page renders and coordinates, visual derivatives, index, state, retry, and deletion through a thread-bound interface. The existing object-store port supplies bytes and gains deletion support; workspace HTTP handles upload/send gating and request/response only. The graph owns sequencing at `ensure_attachment_ready` and the host-controlled visual-evidence read, while parser/OCR/vision adapters and indexing stay in the fin attachment capability. The retrieve capability composes company and thread-attachment candidates through source-specific adapters without duplicating company ranking or moving attachment text to iknow-memory. Host tools validate typed locators and bind active-thread scope; the citation gate distinguishes returned text spans from run-bound visual evidence; API DTOs and web components render `unit` citations and original page/region links. In iknow-memory, the source-read tool owns input/output validation and code-point slicing before MCP response assembly, while storage remains the company source-document authority. No parsing, indexing, or slicing is embedded in the HTTP route or graph node.

# 0089. Prepare thread attachments lazily with page-level visual evidence

Date: 2026-09-25
Status: accepted
Amended: 2026-09-27

Thread attachment upload stores raw bytes only and reports `uploaded`; it invokes no parser, OCR, vision provider, or indexer. When a grounded graph turn makes an attachment eligible, `ensure_attachment_ready` starts or joins a durable, idempotent preparation job keyed by attachment content version, waits without holding the thread execution lock, and resumes the same run when required products are ready. Preparation handles each physical page and region with Docling's standard Heron layout pipeline, CPU Tesseract for scanned text, and fin's configured vision provider scanning every rendered full page; a question requiring detail absent from a stored observation may trigger a high-resolution crop inspection of the original page. Heron locates text, tables, and image regions; the configured vision model determines chart presence and meaning. No local vision or separate picture-classification model is loaded. Fin persists versioned visual observations with original attachment, page, and crop provenance; later runs must retrieve or read the matching observation into the current run, but reuse a sufficient cached observation without uploading the attachment again or repeating vision. Text remains citable only after current-run retrieval/read; generated visual observations use a separate typed evidence path and are never source quotes. Attachment bytes and derivatives remain thread-private, and deletion tombstones block late preparation results. Jev remains outside document handling. This replaces ADR 0084's whole-file PDF classification and ADR 0086's upload-time parsing lifecycle while preserving ADR 0088's typed `unit` locators and bounded text reads.

Amended 2026-09-27: Persist each visual observation's versioned structured coverage, binding each covered visual detail to its inspected page or crop scope and complete target; a numeric value's target includes its chart, series, and category identity, or an equivalent complete identity. After the current run reads an observation, the grounded model names the required detail and complete target; the host deterministically reuses the observation only when coverage matches the requested target and region, while an unknown or incomplete target or region or missing coverage requires a new inspection of the stored original. The initial per-run vision-call budget is 89 (up to 80 full-page calls, 8 crop calls, and exactly one reserved full-page transport retry); vision uses a dedicated port with `FIN_MODEL`, `FIN_BASE_URL`, and `FIN_API_KEY`. Record provider usage and any reported cost per turn; when the provider does not report cost, mark it unavailable rather than zero. A monetary ceiling remains deferred.

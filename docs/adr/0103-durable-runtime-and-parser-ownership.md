# 0103. Durable Runtime and independent parser ownership

Date: 2026-10-20
Status: accepted

Process-local run admission cannot safely support independently restarted API and graph workers, and a LangGraph checkpoint alone does not prove that an operation was accepted, a terminal answer committed, or a parse completed. Adopt an application-owned **Fin Runtime** with PostgreSQL-authoritative operation/run state and an independent parser service with parser-owned job state; keep both in the existing PostgreSQL database under separate schemas, while Redis Streams carries bounded notifications and wakeups rather than business truth. This schema and process split is a hard-to-reverse ownership boundary: it avoids introducing a second broker/scheduler and keeps recovery facts with their owners.

Every graph checkpoint mutation must pass through a mandatory generation-aware adapter that preserves the current synchronous saver interface and, on the same database connection and transaction, validates thread reservation, run/attempt lease, attempt/thread generations, cancellation, and tombstone state before writing. Claims, renewals, cancellation, deletion, and checkpoint mutations share a fixed lock order; no transaction spans model or network work, and there is no direct or fallback use of an unfenced stock saver. Runtime state and checkpoints remain distinct authorities despite sharing one database. This decision does not require an async graph or saver rewrite.

PostgreSQL assigns a durable thread-wide event sequence across client-visible run and lifecycle events; per-run sequence is auxiliary. Each state-projection/revision change, sequence allocation, and corresponding outbox row commits in one transaction, while a thread snapshot reads the projection, revision, and high-water mark from one consistent PostgreSQL snapshot. This prevents a new cursor from silently skipping state; any other unprovable continuity requires `reset_required` plus snapshot recovery. The parser service owns parse-job status, attempts, cancellation, and result existence; fin owns attachment/corpus association, visibility, readiness, indexing, and citation rules. Parser completion first enters fin's durable inbox as pending consumption, never as readiness. Outside PG lock transactions, fin fetches and validates the parser-owned result; both its subsequent short result-adoption transaction and final ready transaction lock the current caller attachment/corpus row and compare-and-swap the expected generation, content version/hash, job association, and non-tombstone/non-cancel state. External validation does not replace either transactional authority check. Indexing and other required readiness work remain outside ownership-lock transactions. Only after all required conditions succeed does fin atomically commit the ready projection, thread event sequence, and outbox/resume intent. Fetch, validation, indexing, and commit failures remain non-ready and reconcile, while duplicate or late results are filtered by job, content version, and generation. Redis Streams delivery is bounded and at least once; no end-to-end exactly-once claim is made, and no RabbitMQ, PGMQ, or second workflow engine is added.

Keep the current single-process guard from [ADR 0101](0101-server-owns-runtime-lifetime.md) until generation-aware checkpoint writes, restart recovery, cross-process concurrency, and browser acceptance evidence pass the rollout gate; this ADR does not retire that guard. Preserve the five OpenTelemetry spans in [ADR 0102](0102-opentelemetry-standard-instrumentation-for-turn-receipt-tracing.md) as diagnostic signals, not tool-attempt measurements; canonical tool outcomes supply metric denominators. The evolving Fin acceptance case set remains separate from the real authorized **评测数据集** and must reach at least 50 independent business cases before its campaign can pass.

Authority: the operator's decisions and closed runtime, parser, reconnection, and acceptance tickets on 2026-10-20. See the [server runtime contract](../../specs/qa-chain-server-runtime.md). The four-stage work sequence is tracked in the [Runtime reliability map](../wayfinder/harness-runtime-reliability-map.md). This ADR records target design only; no implementation, capacity measurement, or acceptance test is claimed.

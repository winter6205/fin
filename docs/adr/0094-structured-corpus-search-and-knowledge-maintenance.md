# 0094. Structured search and knowledge maintenance use the ingested corpus

Date: 2026-10-03
Status: accepted

fin is the knowledge-QA entry point and iknow owns the ingested knowledge corpus (ADR 0090). The former `sql` direction queried a separate enterprise ledger, creating a second primary data path instead of searching the product's corpus. Structured search will query structured representations retained from that same ingested corpus through the existing retrieve boundary: the model submits a typed query request, and iknow validates it and executes a bounded, parameterized, read-only query. This partially supersedes ADR 0059 **only** where it defines D/`sql` as a separate business-SQL source and says figures present only in ingested documents must remain on graph; A/B/C routing, their index-artifact behavior, the closed-set mode tokens, and the single retrieve entry point remain in force.

## Decision

- The ingested corpus in iknow is the source of both graph retrieval and structured search. A separate enterprise database is not the primary `sql` source. The current contract-expiry implementation is a legacy path pending a replacement SPEC; this ADR does not change runtime behavior or waive the pending acceptance.
- The model expresses a typed query request. The backend owns field and operation validation, access bounds, query compilation, and read-only parameterized execution. The model does not author executable SQL. Initial query capabilities and their exact request and response shapes belong in the replacement SPEC.
- Queries may traverse explicitly supported existing relationships. The selected result subject determines result identity, deduplication, pagination, and count semantics. Distinct relationships remain distinct; repeated provenance is deduplicated by source-version and location identity, while distinct sources and versions remain attached to the fact they support. Similarity or occurrence count alone does not establish identity or truth.
- Source updates preserve versioned provenance to the original evidence. A maintenance decision records a change of interpretation or lifecycle state without erasing its historical basis; source replacement must not silently break an older fact's evidence link. Retention and historical reads remain subject to the existing access and deletion boundaries.
- Knowledge maintenance is owned by iknow and coordinates source updates, provenance and identity handling, conflict detection and recorded decisions, and derived graph/search projections. These responsibilities remain separate capabilities behind the maintenance boundary. Existing job, outbox, reindex, and maintenance mechanisms may be reused; this ADR does not mandate a new global service, queue, or model provider.
- Ingest and source updates trigger durable incremental conflict checks. Checks produce version-bound status and evidence; they do not silently replace assertions. Conflicting assertions and their sources remain queryable until an explicit, versioned maintenance rule or decision resolves them. There is no default newest-wins rule. Queries remain read-only and expose pending, failed, or stale check status where applicable. A stale job cannot publish a result for a newer source version. Search readiness and conflict-check readiness are distinct states.
- Exact statistics operate on the complete matching set and on an explicitly identified subject. Numeric aggregation requires typed numeric values and defined units and record identity; an untyped extracted value is not sufficient evidence for a sum. Document-type-specific field extraction and broader business-field catalogs are future extensions, not prerequisites to the initial structured-search contract.
- ADRs 0091–0093 continue to govern the existing database-row evidence and snapshot identity contracts. This ADR neither changes those contracts nor decides how a future structured-corpus result maps to them; the replacement SPEC must resolve that mapping explicitly before implementation changes it.

## Consequences

- The structured-search path must reuse corpus identity and provenance rather than introduce a second primary source. Exact filter, relationship, aggregate, pagination, status, and evidence semantics must be specified before the replacement contract is buildable.
- Existing `sql` code and its dedicated contract-expiry acceptance are not evidence that same-corpus structured search is implemented. A new acceptance boundary must exercise the actual ingested corpus while preserving the previously agreed acceptance obligations.
- Automatic conflict adjudication, a specific LLM or Jev dependency, a maintenance UI, and document-type-specific extraction rules remain open or out of scope until separately specified.

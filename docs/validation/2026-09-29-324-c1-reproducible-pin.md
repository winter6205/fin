## A defect the pin itself had: `--require-hashes` enforced 1 of every 26 hashes

The first full builds of the new Dockerfile **failed**, and the failure was in
the generated lock, not in the environment:

```text
ERROR: THESE PACKAGES DO NOT MATCH THE HASHES FROM THE REQUIREMENTS FILE.
    docling-parse==7.22.1 from https://files.pythonhosted.org/.../docling_parse-7.22.1-cp312-...whl
        Expected sha256 14457f76eda6b4eb24d9a04a8cb150bc92efa4d177743493aebc487d959754bd
             Got        db7428f727e115bfec15b9db57949ceee547ae2457f5c5b7f32eb70e5acc6ff6
```

The wanted hash **was in the lock**, at line 68 of a 26-hash entry — verified by
reading the file, and `Got` matches the sha256 PyPI publishes for that exact
wheel (independently recomputed by downloading it and hashing the bytes:
`db7428f7…`, identical). All 26 lock hashes were diffed against the 26 files
PyPI actually serves for `7.22.1`: exact match, nothing extra, nothing missing.
The lock data was entirely correct and pip still rejected it.

The cause is a line-continuation rule, measured rather than assumed. pip
terminates a logical requirement at the first physical line lacking a trailing
`\`, so **every line except the last must carry a continuation; the last line
does not need one.** The generator emitted continuations on every line *except*
the last, which meant the requirement ended at the first hash line and the
remaining 25 `--hash` lines became standalone lines with no requirement to
attach to.

Measured, offline (`--no-index --find-links`, real wheel, real sha256, with
wrong-hash negative controls so a false pass is impossible):

| entry shape | pip result |
| --- | --- |
| one hash, no `\` on that last line | accepted (exit 0) — a last line without `\` is legal |
| correct hash first, wrong hash second, no `\` on last | accepted (exit 0) |
| **wrong hash first, correct hash second**, no `\` on last | **accepted (exit 0)** |
| same, with `\` on the last line | accepted (exit 0) — identical |
| two wrong hashes | rejected (exit 1), both listed as `Expected … or …` |
| wrong hash on line 2 (no `\`), correct on line 3 (with `\`) | rejected (exit 1), line 3 discarded |

Two conclusions follow. pip honours **all** hashes on a requirement as
OR-alternatives regardless of position — position is irrelevant. And the
continuation requirement is about the non-last lines, not the last one.

What the discarded-hash bug actually caused here is worth stating precisely,
because it is the opposite of a silent bypass: a **fail-closed** error. pip
compared the artifact against hash 1 alone, hash 1 was not the wheel it
downloaded, and it **rejected a correctly-hashed legitimate package and stopped
the build**. Nothing wrong was installed. pip also says so — it emitted 25
`WARNING: … has --hash but no requirement, and will be ignored` lines, so the
truncation was observable in stderr; the original build log captured only the
`ERROR`, which is why it read as a silent drop at the time.

The security concern that remains is real but narrower than "enforces almost
nothing": a lock that pins 1 of 26 hashes accepts a **narrower** set of
artifacts than it appears to, so a legitimately re-uploaded wheel would be
refused rather than an unexpected one admitted. The fix is unchanged — every
hash line now carries a continuation and entries are separated by a **blank
line**, which terminates the requirement without dropping a hash, with
`pin.py`'s line joiner updated to match (blank line wins over a trailing
continuation). `test_committed_lock_covers_every_frozen_requirement` now catches
the regression, because a swallowed entry reads as one requirement with a bad
hash token rather than two.

## What an adversarial verifier found, and what this record got wrong

A verifier executed the code rather than reading it. The mechanism held — the
`--require-hashes` fix above is real, driving an actual
`pip install --dry-run --ignore-installed --require-hashes` in the pinned image:
exit 0 on the fixed lock, and a byte-for-byte reproduction of the original
`Expected sha256 14457f76… / Got db7428f7…` failure from the pre-fix lock. But
three statements about it were stronger than the code, which is the exact
failure mode C1 exists to remove.

**This record's own Leftovers 5 said the TableFormer swap was caught by
"nothing: not the driver, not `build.sh`, not `pin.py verify-models` (which
reads the metadata the fetch itself wrote…)".** That parenthetical described the
*pre-repair* `verify_models`; the sentence was still in the document after
commit `5b47c91` made the function hash the payload, and it contradicted this
record's own §*A third gap* five pages earlier. The verifier proved the new code
catches it: the real 212,758,388-byte file was copied to `/tmp`, its bytes
overwritten with the sidecar left intact, and `tableformer-accurate: the payload
… hashes to 08d723a7…, not the pinned 2a7d6c92…` was reported. It also said the
gap "has no live owner", which stopped being true when `build.sh:104-109` began
running `verify-models` on every build. Leftovers 5 has been rewritten to the
residual that is actually open: the *mid-run* detection gap in `driver.py:385`,
which hashes only paths containing `layout`, so a swap performed after the
build's gate and during a measurement is not reported in the per-run JSONL. The
build-time gate is closed.

**A test credited itself with a rule it did not protect.**
`test_self_check_fails_when_the_lock_is_corrupted` carried the docstring claim
that "removing the `--require-hashes` rule fails this test". The verifier
deleted that rule from a copy of `pin.py` and all 56 tests still passed. The
test corrupts `requirements.lock` by dropping hashes, which trips
`validate_requirements_lock_text` (`pin.py:399-401`) — a different rule, about
lock entries. The docstring is corrected, and the missing leg is added:
`test_a_dockerfile_without_require_hashes_is_rejected`, plus a companion that
asserts the mutated Dockerfile violates *no other* Dockerfile rule, so the
`--require-hashes` rule is the isolated cause. Writing it exposed a further
weakness in that rule itself: it was a bare `if "--require-hashes" not in text`
over the whole file, so the committed Dockerfile satisfied it partly through a
*comment* that mentions the flag. It is now `_installs_under_require_hashes`,
which requires the flag and the lock reference on the same non-comment
`pip install` line.

**The apt Dockerfile↔lock check was one-directional and only saw `=`-bearing
tokens.** Five mutations all validated clean: dropping the `=` from
`tesseract-ocr-chi-sim=1:4.1.0-2` (a silent downgrade to unpinned), separating
name and version with a space, deleting a pinned line outright, adding a pinned
package the lock never requested (`wget=1.99`), and adding a bare unpinned one
(`nano`). `apt-packages.lock` was therefore decorative for the OS layer in
exactly the cases that matter, while `PIN_MANIFEST.md` and this record both
read as a closed loop. `validate_apt_install_line` now requires every non-flag
token on the line to be version-pinned, every pinned name to be in
`[requested]` at an equal version, and every `[requested]` entry to appear on
the line. `UNVERSIONABLE_APT_TOKENS` is the named exemption list for a token
that cannot carry a version; it is deliberately empty, and a test asserts it
stays empty so an exemption is a one-line decision rather than a build failure
discovered later.

## A third gap the issue did not name: the model fetch was never pinned

Issue 324's acceptance requires pinning "externally fetched model revisions and
content hashes". The revisions were *recorded* but not *bound*:

* `PIN_MANIFEST.md` listed Heron as `docling-project/docling-layout-heron @
  main`. `main` is a movable branch. The resolved commit `8f39ad3c…` sat beside
  it, but recording a commit that was observed is not pinning the fetch to it.
* The fetch command — the one `run_measured.sh:207-219` actually runs — took no
  revision at all: `models download --output-dir /models layout tableformer`. A
  fresh host fetching today gets whatever `main` points at now.
* The asymmetry is the tell: TableFormer was already fetched at the immutable
  tag `v2.3.0`, and **Heron — the one model the layout stage actually depends
  on — was the unpinned one.**
* The recorded sha256s (`00333a43…`, `2a7d6c92…`) were facts about the past,
  not gates on the next fetch.

**Fixed:** `models.lock` declares all 4 artifacts at a 40-character commit with
their payload sha256, `pin.py` refuses movable refs outright, and
`pin.py verify-models` checks the fetched weights, and now **hashes the payload
itself** rather than trusting the metadata sidecar's own ETag claim — a swapped
`.safetensors` with an intact sidecar is detected. Verified against the live
host cache (exit 0), and against synthetic moved-commit, swapped-payload,
payload-under-intact-metadata, empty-metadata and absent-metadata cases (all
correctly fail).

**BLOCKER 1 (open, un-owned — NOT a neutral deferral).** The fetch is still not
bound to a revision. `run_measured.sh:213` runs

```bash
"${IMAGE}" models download --output-dir /models layout tableformer \
```

with no `--revision`, so a fresh host silently fetches whatever `main` points
at today. **No automated check binds the fetch to a commit**: `pin.py
verify-models` is run against the cache *after* the fact, so it reports a moved
Heron — it hashes the payload against the pinned sha256 and fails — but a fetch
that lands on the wrong commit still performs a full measurement before anything
notices, and a fetch that moves the payload is only caught if the build's gate
runs afterwards. It is a check on the cache, not a constraint on the fetch.
`run_measured.sh` is outside this task's write surface, so this item is filed
here as an open blocker with a named owner still required, rather than as a
note.

The exact change that closes it, for the `run_measured.sh` owner:

```bash
# in the fetch docker run block (run_measured.sh:206-214), replace
        "${IMAGE}" models download --output-dir /models layout tableformer \
# with an explicit per-model revision binding, e.g.
        "${IMAGE}" models download --output-dir /models \
            layout --revision 8f39ad3c0b4c58e9c2d2c84a38465abf757272d8 \
            tableformer --revision fc0f2d45e2218ea24bce5045f58a389aed16dc23 \
# and immediately after the fetch succeeds, before the measurement:
#   python3 scripts/g4_pipeline/pin.py verify-models \
#       --pin scripts/g4_pipeline/models.lock --cache-root "${MODEL_CACHE}"
```

The commits are the `revision` fields of `models.lock`, which is the single
source of truth for them. The verifier call is the same one `build.sh` now runs
before its identity check; running it after the fetch rather than only at build
time is what makes it a gate on the fetch. Until both land, **the model pin is
declared and verifier-tested, but not fetch-enforced.**

## Two sources of truth that were never compared with each other

Every input in the pin is now individually validated, which is necessary and
not sufficient: L7 was not a malformed lock, it was a *correct* freeze and a
*correct* prose claim that disagreed. Three such pairs existed, and none of them
was cross-checked:

1. **`PIN_MANIFEST.md` vs `image-pin.json` / `results/image_identity.txt`.** The
   guard regexed `sha256:` + 64 hex, but the manifest writes its digests
   truncated (`sha256:8e10185f…`), so it matched nothing and
   `test_manifest_does_not_contradict_its_declared_sources` **could not fail**.
   Now: the truncated form is matched and resolved as a prefix against the known
   ids, the guard is scoped to the manifest's §1 identity section (the rest of
   the document legitimately quotes probe-build and diffID digests as evidence),
   `self_check` fails if the guard can see no digest at all, and
   `test_a_stale_truncated_digest_in_the_manifest_is_caught` is the negative
   leg.
2. **`apt-packages.lock`'s `[requested]` vs `[installed]`.** The version check
   merged the two dicts, so `[installed]` shadowed `[requested]` and a lock
   could request `curl=8.14.1-2+deb13u5` while recording `curl=1.0.0` as
   installed and still validate — L7's exact shape, inside the new mechanism.
   Now each section is validated independently and
   `lock.resolve(name) == lock.requested[name]` is asserted for every requested
   package, citing both versions on disagreement.
3. **`Dockerfile`'s apt `install` line vs `apt-packages.lock`.** The Python
   layer got the treatment the OS layer lacked: a Dockerfile installing
   `curl=99.99.99` validated cleanly against a lock naming `8.14.1-2+deb13u5`.
   `validate_dockerfile_text` now takes the parsed apt lock, and the check is
   three-way, because the first version of it was one-directional and only read
   tokens that already carried an `=`. Five mutations all validated clean under
   it: dropping the `=` (`tesseract-ocr-chi-sim=1:4.1.0-2` → bare
   `tesseract-ocr-chi-sim`, a silent downgrade to unpinned), separating the
   version from the name with a space, deleting a pinned line outright, adding
   a pinned package the lock never requested (`wget=1.99`), and adding a bare
   unpinned one (`nano`). `validate_apt_install_line` now requires **every**
   non-flag token on the line to be version-pinned, **every** pinned name to be
   in `[requested]` at an equal version, and **every** `[requested]` entry to
   appear on the line. `test_apt_dockerfile_mutations_are_rejected` carries one
   negative leg per mutation.

## The model gate is no longer skipped, and it is no longer last

Two further corrections to the same gate:

* **Ordering.** The gate ran *after* `compare-image-id`, which fails every build
  on this builder, so the model content hashes were never checked on any real
  build — only by a hand-run command. It now runs first; `build.sh` verifies the
  models, then the identity.
* **A missing cache is a failure, not an absence of a check.** The gate was
  guarded by `if [[ -d "${MODEL_CACHE}" ]]` with an `else` that logged a `note:`
  and continued, so on any host without a warm cache the model pin was never
  checked at all. It now exits **75** with a named `FATAL`. The right long-term
  home for the gate is `run_measured.sh`'s fetch preamble, which may also bind
  the fetch to a `--revision` — see *BLOCKER 1*.

## Builder provenance is still prose-only

The issue asks for package, OS, base, builder, model and source provenance
checkable "without prose-only pins". Five are mechanical now. **Builder identity
is not**: the engine version (`29.1.3`) and the legacy-builder fact live only in

## The builder experiment — is byte-identity reachable?

Two clean `--no-cache` builds of a deliberately trivial 2-layer Dockerfile over
the same digest-pinned base, chosen to isolate the builder from every pin
variable (no apt, no pip, no network-dependent step):

```dockerfile
FROM python:3.12-slim
ARG MARKER=1
RUN echo "$MARKER" > /opt/marker && echo "second layer" > /opt/second
```

| | build 1 | build 2 |
| --- | --- | --- |
| image id | `sha256:a0f088b84107…` | `sha256:ed2ae6867966…` |
| `created` | `2026-09-29T20:55:47.408482569+08:00` | `2026-09-29T20:56:57.577821291+08:00` |
| exit | 0 | 0 |

**The two ids differ.** The cause was isolated, not inferred:

* **The 4 base layers are byte-identical.** `docker image inspect
  --format '{{range .RootFS.Layers}}…'` differs only in the 5th entry:
  build 1 `sha256:6901e9d2…`, build 2 `sha256:08c4005e…`. The first four — the
  entire inherited base — hash the same in both.
* **The differing `RUN` layer has byte-identical *contents*.** Extracting layer 5
  from both saved tars and running `diff -r` reports no difference: `opt/marker`
  (2 B) and `opt/second` (13 B) hold the same bytes in both. Only the mtimes
  differ — `1790686725.8141293580` vs `1790686725.9301293600`, i.e. the ~116 ms
  between the two extractions, and the parent dir `1790686546` vs `1790686616`,
  i.e. the 70 s between the two builds. Layer tarballs are 168 bytes each.
* **The image config differs in exactly the timestamp fields.** Diffing the two
  OCI config blobs: `created` differs, each `history[].created` differs, and
  `rootfs.diff_ids` differs. Nothing else differs — and both configs are
  **6025 bytes**, the same bytes with a different timestamp substituted. The
  image id *is* the sha256 of that config.

So the wall-clock time is written into **both** the layer tar (via mtimes) and
the config blob, and the config is what the id hashes. That is a property of the
builder, not of the pin: no Dockerfile content can suppress it.

**`SOURCE_DATE_EPOCH` does not help.** Two further clean builds with
`SOURCE_DATE_EPOCH=1700000000` exported, 45 s apart:

| | build 3 | build 4 |
| --- | --- | --- |
| image id | `sha256:1b0668abbda2…` | `sha256:09e027d46573…` |
| `created` | `2026-09-29T20:59:21.67286393+08:00` | `2026-09-29T21:00:06.641672101+08:00` |

The legacy builder ignores `SOURCE_DATE_EPOCH`. It is a BuildKit/OCI-archive
convention, and this host has no BuildKit.

## Build context

There was no `.dockerignore` anywhere in the repo, so the build context was the
entire `scripts/g4_pipeline/` directory — all 106 committed `results/`
artifacts, including per-run page images, shipped to the daemon on every build.
This does **not** affect the image id: the Dockerfile copies exactly one file
(`requirements.lock`), and a context file that is never `COPY`d cannot reach a
layer. The new `.dockerignore` excludes `results/` and the harness scripts,
taking the context from ~large to **236 kB**. It is a build-time and
hygiene change, deliberately recorded as *not* a determinism change.

## Test contract — hermetic, no docker, no network

`tests/host/test_g4_pipeline_pin_contract.py`, 65 tests, all in the default
`uv run pytest -q` suite. It loads `pin.py` by path (docling stays out of
`src/`, and the module must not be importable as `fin.*`) and reads only
committed files plus `tmp_path` fixtures. It covers all six behavior classes:

| Class | Cases |
| --- | --- |
| Normal | lock covers the freeze by name and version; every entry hashed; hashes are 64-char lowercase hex; Dockerfile installs the lock under `--require-hashes` with no inline `==`; base is digest-pinned; apt lock names an immutable mirror and records dependencies as well as the 8 requested; declared expectation differs from the committed snapshot; a matching digest passes the real CLI |
| Failure | digest drift is detected (the exact L7 pair); empty lock; comment-only lock; lock entry with no hash; entry with no version; empty apt lock; apt lock with no mirror; Dockerfile with a mutable tag; identity snapshot with no `image_id=`; freeze line that is not a pin |
| Boundary | lock declaring 0 packages; lock omitting `docling`/`torch`/`torchvision`/`pytesseract`; lock-vs-freeze disagreement; trixie's `libglib2.0-0` → `libglib2.0-0t64` virtual-provide rename |
| Exception | unparseable lock text; non-UTF-8 lock bytes; `self-check` on a corrupted lock copy (negative leg, asserted through the real CLI); model pin reading a **moved commit**, a **swapped payload**, **empty metadata**, and **absent metadata** — the last two asserting failure rather than a default, per the driver's "a failed reading is never a zero"; the Dockerfile claiming a `pin.py` check that does not exist |
| Duplicate/second run | `build.sh` delegates to `pin.py` rather than inlining rules; `build.sh` never truncates a committed snapshot with `>`; `build.sh` is syntactically valid; `build.sh` runs the model gate before the first `exit 75`, so it is reachable rather than dead code |

The two tests that matter most for the gate's tautology concern:
`test_expected_image_id_is_declared_outside_the_build_output` asserts the
declared expectation is not the same string as the committed snapshot (a check
between two identical strings can never fail), and
`test_drift_check_is_reachable_and_fails_loudly` drives the real CLI with a
mismatched pair and asserts a non-zero exit **and** a `FATAL` line on stderr.

## Limitations / leftovers

1. **The exact-digest acceptance is not met, and is not meetable here.** The
   builder writes wall-clock time into both the layer tar and the hashed config
   blob. Reaching byte-identity needs BuildKit (`docker buildx` + a
   `BUILDKIT_INLINE_CACHE`/`--output type=image` build, or `docker buildx build
   --provenance=false` with a pinned `SOURCE_DATE_EPOCH`). This is the operator
   decision below. This record does not treat the pin as complete on the strength
   of its inputs alone.
2. **`8e10185f…` is not reachable even in principle from these inputs.** It was
   produced by a build whose base was a *mutable tag* and whose Python
   resolution was *unpinned*, so the bytes it names are not derivable from any
   declaration now in the tree. It is retained as the expectation because the
   issue forbids replacing it silently, not because the new inputs can produce
   it.
3. **The `requirements.lock` was generated from the drifted freeze.**
   `results/image_pip_freeze.txt` records `docling-parse 7.22.1`, `Faker
   40.40.0`, `regex 2026.9.29` — the post-drift resolutions. The lock therefore
   freezes *the drifted state*, correctly and reproducibly, but it does not
   restore the `7.21.0` / `40.39.0` / `2026.9.10` that L7's image had. Those
   three are not separately recoverable without a dated PyPI snapshot; if the
   operator wants them back, that is a decision, not a rebuild.
4. **`repo_digests` was dropped from the identity snapshot.** The previous
   `build.sh` recorded `docker image inspect .RepoDigests`, which for a locally
   built, never-pushed image echoes the image id back — it looks like registry
   provenance and is not. Recording it would have made a local build look
   attested.
5. **TableFormer weights are not re-verified *per run*.** The residual gap is
   narrower than it was, and the earlier wording of this item was wrong.
   `verify_models` no longer reads the download metadata's word for the payload:
   it hashes the `.safetensors` itself, so a swapped file with an intact sidecar
   is rejected — demonstrated on the live 212,758,388-byte artifact, which was
   copied, overwritten, and reported as `the payload … hashes to 08d723a7…,
   not the pinned 2a7d6c92…`. `build.sh:104-109` runs that check on **every**
   build, so a swap made before a build cannot reach an image. What is still
   missing is the *mid-run* detection: `driver.py:385` hashes only paths
   containing `layout`, so `tableformer_accurate.safetensors` appears in the
   per-run JSONL with a size and no sha256, and a swap performed **after** the
   build's model gate and **during** a measurement is not reported per run. This
   was originally filed as "C2's surface, not this task's", and C2 closed out as
   blocked evidence (`docs/validation/2026-09-29-g4-324-c2-pipeline-gold.md`,
   L5) without wiring it, so the per-run leg still has no live owner. Filed here
   with the expected value so a future owner can act without re-deriving it:
   `tableformer_accurate.safetensors` sha256
   `2a7d6c924b3cd12fb99a09280ca9c33a89c5d60b93253617d2e088c1a40374d9`
   (independently confirmed equal to the HuggingFace Hub ETag and to a local
   `sha256sum`; it is the `file_sha256` of `[tableformer-accurate]` in
   `models.lock`, which is the single source of truth for it). `driver.py` is
   outside this task's write surface, so the fix is not made here.
6. **The installed dpkg set is recorded but not enforced.** `apt-packages.lock`
   holds the full 188-package set measured from the recorded image's apt layer,
   and `build.sh` snapshots the build's own `dpkg-query` output to
   `results/image_apt_status.txt`, but nothing compares them and nothing fails
   when they disagree. What actually binds the OS layer is the
   `snapshot.debian.org` timestamp plus the 8 exact `=version` pins in the
   `apt-get install` line. `Dockerfile` and `run_measured.sh` are the wrong
   places to close this; it would be a new `pin.py` subcommand plus a
   `build.sh` call, and no one currently owns it.
7. **`gen_requirements_lock.py` is not covered by the default suite.** It is the
   one file in this directory that uses the network, by design — it reads PyPI
   and the PyTorch index to turn a freeze into a hash-locked file. The build
   never calls it. Its output is verified by
   `test_committed_lock_covers_every_frozen_requirement`.
8. **The apt snapshot timestamp was chosen, not inherited.** `20260929T083940Z`
   is the latest `snapshot.debian.org` capture of `debian` at the time of the
   work, chosen because all 8 requested packages resolve there to exactly the
   versions the recorded image already had, so the pin anchors to the existing
   image rather than silently upgrading the OS. All 8 were confirmed against the
   `trixie/main/binary-amd64` Packages index at that snapshot.

## The decision required

**`8e10185f…` is unreachable, and no build on this host can produce any fixed
image id. The operator must choose which of these the contract becomes:**

- **(a) Change the builder.** Install `docker buildx` and build with BuildKit,
  which honours `SOURCE_DATE_EPOCH`. Then a fixed expected digest becomes
  reachable and `image-pin.json` needs only one new baseline for the *new*
  builder, recorded with its own inputs. This is the only option that keeps the
  "byte-identical image identity" clause as written.
- **(b) Change what is compared.** Accept the per-layer `diffID` set plus a
  declared base digest as the identity, and drop the exact-image-id clause. The
  probe above already shows the base layers are stable; the `RUN` layers are not,
  so this clause would need "and the RUN layers' *contents*", which is a weaker
  and differently-shaped promise.
- **(c) Re-baseline.** Adopt a new expected digest from a build made under the
  new mechanical pin, with its own immutable inputs and measured-output
  expectations. This is the issue's explicitly permitted path — "A changed
  tool/model version may establish a new baseline only after that decision" —
  and it is the only option that does not require changing the builder, but it
  gives up byte-identity across builds, so the "two clean builds" clause cannot
  be satisfied by it either.

Until one is chosen, `build.sh` exits 75 on every build, which is correct: the
pipeline cannot currently prove it built the image it declared.
